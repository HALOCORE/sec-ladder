## 0a. What this row is, in one paragraph

A `FIND` caches the address of the record it found. A later `USE` reads through
that address. **Deleting a key from a binary search tree does one of two things
to the record that held it, and which one is chosen by the DEGREE of the
victim** — and `c/kernel.c` omits the line that would notice either. The whole
of the row is that the two need *different* conjuncts, and that the second
conjunct is invisible to every mechanism this project owns.

## 1. The two design questions, and the criterion they were settled on

`TASK_137` re-opened two decisions `TASK_136` had closed. Both were settled
before anything was built, and the losing arms are shipped as measured controls
(`controls/arms.py`) rather than described.

### 1a. WHERE the safety line goes — the read path, and here is the criterion

**There were TWO exact candidates**, not one, and `controls/arms.json` confirms
it on the shipped kernel: the read-path line (`R1h`, shipped) and the write-path
line (`H2`) are both **exact on every window measured, with zero ASan lines**.
Exactness does not decide it. The criterion does:

> ### **The shipped R1h must be the artefact the row's headline is a claim about, and the same claim must be legible in every rung.**

A benchmark row's product is its `c/kernel.c` ↔ `c/kernel_hardened.c` diff plus
the numbers hung on it. A headline that describes a line the tree does not
contain is an anecdote rather than a measurement, and this project has a named
failure class for publishing a *reading* instead of the measured object
(`.memory/03-measurement.md` entry 12). Applied:

| | read path (`R1h`, SHIPPED) | write path (`H2`) |
|---|---|---|
| **the row's headline** — *`p27`'s read-path line needs ONE conjunct, `p29`'s needs TWO* | **is the shipped diff.** `p27`'s `&& live[h] == 1` and `p29`'s `&& live[g_slot] == 1 && tab[g_slot][0] == g_key` sit in two shipped files and can be diffed | describes an arm the tree does not contain; `p29`'s shipped diff would be a pointer-nulling statement inside `REMOVE`, which has no `p27` counterpart at all |
| **legibility across rungs** | every rung has the line and they differ in exactly the interesting way: C spells both conjuncts, **safe Rust gets the first from `Option` and must write the second by hand**, R5 turns the first into `perms.dom().contains(g_slot)` and the second into a value equality | the safe rungs would null a cached *index*, which is neither what the language gives them nor what C does |
| **R5 tractability** | the check discharges its own precondition **locally**: `live[g_slot] == 1` is what `tracked_borrow` needs, and nothing else is required | the read is licensed only by `g_saved != NULL`, which needs a global existential — *some live slot's record is this address* — re-established by every mutation. ⚠ **Argued, not measured: no `H2` R5 was built** (§8) |
| **exactness** | exact | exact — **not a discriminator** |
| **R1 → R1h is one line at one site** | yes | yes — **not a discriminator** |

⚠ **Two of the five rows do not discriminate, and saying so is the point**: the
choice was made on comparability and legibility, not on correctness or on cost,
and **no cost axis was measured on either arm** (§8).

✅ **And the losing arm is kept, measured, and re-derived from the shipped
source**: `controls/arms.py` builds `H2` by splicing the write-path line into
`c/kernel.c` itself, so it cannot drift away from the rung it varies.

### 1b. Whether `tab[]` is nulled on the free — NO, and it is now measured

`p27`'s `c/kernel.c` argues by name that *"nulling `tab[h]` on close would turn
the stale read into a NULL dereference, which is a **crash**, not a
use-after-free, and a different bug class."* `TASK_136`'s draft `p29` nulled it
anyway. **p29 keeps `p27`'s convention, and there are now three reasons rather
than one:**

1. **The bug class, measured rather than argued** (§2c): with `tab[cur] = NULL`
   added, the one-conjunct control stops reporting `heap-use-after-free` and
   starts reporting `SEGV`. `p27`'s sentence, reproduced on `p29`'s kernel.
2. **It is what makes the identity conjunct's danger visible at all.** With
   `tab[]` write-once, `tab[g_slot][0]` and `g_saved[0]` are *the same load from
   the same address*, so the only thing separating the shipped safety line from
   a use-after-free is the short-circuit order (§2b). Null the table and that
   sharpness is replaced by a different crash.
3. **It is what makes the R5's central invariant free.** `wf`'s last conjunct is
   `st.gh ==> g_saved == tab[st.gs as int]`, and with `tab[]` written once per
   slot **no operation has to re-establish it** — not the insert, not the
   splice, not the free. Nulling on free would make it conditional on liveness
   and would have to be re-proved at every deletion.

⚠ **The interaction the previous design missed**: the read-path safety line can
be spelled through `tab[g_slot] != NULL` instead of `live[g_slot] == 1`, and
that spelling *requires* the nulling. It is therefore not available here, and
`live[]` — `p27`'s own spelling — is the one that ships.

## 2. THE RESULT: two conjuncts, and they fail in different currencies

### 2a. Four mechanisms, one fault line

| mechanism | use-after-FREE (0/1-child victim) | use-after-RECYCLE (2-child victim) |
|---|---|---|
| ASan | `heap-use-after-free`, aborts | **silent** |
| Miri | `memory access failed: alloc… has been freed` | **silent, and the answer is wrong** |
| safe Rust's `Option` discriminant | the slot is `None`; the class cannot occur | **`Some`, and it is somebody else's record** |
| Verus's linear `PointsTo` | `rec_free` consumed it; the read is unprovable | **the permission survives; nothing linear objects** |

⚠ **The Miri row needed its own control and did not have one until this task.**
The gate runs Miri over `unsafe.rs`, which is the CORRECT rung and has no UB to
find on any input — eight `ok, no UB` rows that say nothing about either bug
class. `controls/miri_arms.py` runs Miri over `unsafe.rs` **with the USE path's
two conjuncts deleted**, i.e. `c/kernel.c`'s bug written in Rust, on the same
adversarial inputs, with the shipped file as the must-be-clean control:

| variant | `adversarial-uaf.bin` | `adversarial-succ.bin` | `adversarial-recycle.bin` | `small.bin` |
|---|---|---|---|---|
| **shipped `unsafe.rs`** (the must-be-clean control) | no UB, `5933090192955198528` | no UB, `9600548768877911104` | no UB, `2755550117516839872` | no UB, `14724091388107228810` |
| **`r1line`** — both conjuncts deleted | ⚠ **UB**, `memory access failed: alloc… has been freed` | ⚠ **UB**, same | ✅ **no UB — and the answer is `2751827421526092736`, which is NOT `2755550117516839872`** | no UB, identical |

*(`controls/miri_arms.json`, `miri 1.99.0-nightly (d453bdd8f 2026-08-14)`,
`n_iters` rewritten to 4, `-Zmiri-disable-isolation`, `MIRIFLAGS` unset — the
gate's own invocation.)*

> ⚠⚠ **THE RECYCLE ROW IS THE ONE THAT MATTERS: Miri runs the buggy program to
> completion, reports nothing, and it prints a DIFFERENT NUMBER.** The strongest
> memory-safety instrument in the matrix, on the exact source that has the bug,
> on the exact input that triggers it — silent.

✅ **Both controls this probe owes are present and both behave.** The **positive**
control is `r1line` on the two use-after-free inputs: Miri *does* see UB in this
program, so its silence on the recycle input is a fact about the bug class and
not about the instrument. The **negative** control is the shipped `unsafe.rs`,
clean on all four, so the UB is a fact about the deleted conjuncts and not about
the kernel.

**All four are mechanisms about the ALLOCATION, and the two-child splice never
touches the allocation** — it copies the in-order successor's key and val *into
the victim's record* and frees the *successor*. That is why the safety line
needs a second, non-linear conjunct, and it is `p29`'s whole contribution over
`p27`.

### 2b. Dropping either conjunct is measurable harm, and the two harms are not the same kind

counted with `count('AddressSanitizer')` and never with `head`. Every arm is
`c/kernel.c` with ONE line substituted; the numbers are in

| `H2` — the write-path arm | R1's test, plus one nulling line inside `REMOVE` | **0** | 0 / 104 | 0 / 18 | **0** | — |

✅ **`R1h` and `H2` are BOTH exact and both fire ASan zero times**, which is why
§1a had to be settled on a criterion rather than on a measurement.
⚠ `liveonly`'s 6 wrong answers on UAF-classified windows are windows that
contain a recycle event *as well as* a use-after-free; the classification takes
ASan first.

> ⚠⚠ **THE TWO CONJUNCTS FAIL IN DIFFERENT CURRENCIES, AND NEITHER SUBSUMES THE
> OTHER.** Drop the **liveness** conjunct and the harm is *memory-unsafety and
> usually not a wrong answer* — the freed bytes still hold the old record often
> enough that the checksum survives. Drop the **occupant-identity** conjunct and
> the harm is *a wrong answer and never a memory error* — every recycle window
> diverges and ASan says nothing at all.

✅ **And with `tab[]` write-once, `tab[g_slot][0]` and `g_saved[0]` are the same
load from the same address** — which is why the `keyonly` and `deref` arms
behave alike. **The only thing that makes the shipped line safe is that `&&`
short-circuits and the liveness conjunct is first.** At R5 that ordering is not
even a choice (§6).

### 2c. `tab[cur] = NULL` changes the BUG CLASS — `p27`'s argument, measured

The `nulltab_*` columns above are the same arms with `tab[cur] = NULL;` restored
after the free. Only one arm moves, and it moves in exactly the way `p27`
predicts: **`keyonly`'s sanitizer class changes from `heap-use-after-free` to
`SEGV`**, and its wrong-answer count jumps, because a NULL dereference is a
crash rather than a silent read. `p27` argued it in prose — in its own
`c/kernel.c` header and inside its hashed `why` — and nothing had measured it on
a second kernel until now.

✅ **AND THE RECYCLE DIVERGENCE IS STABLE ACROSS THE WHOLE MATRIX, NOT JUST
ACROSS RUNS.** The gate's own stage-4 table on `adversarial-recycle.bin`:
`model.py` expects `6826524771972934656`, the six checked cells all print it,
and **all eight buggy C cells — gcc and clang, `-O0` and `-O3`, isolated and
whole — print `10466247628510718976`.** One wrong value, eight cells, two
compilers, two optimisation levels, two inline modes. On
`adversarial-uaf.bin`/`-succ`/`-many` the same table reports *"4 distinct

reproduces, and it reproduces further than the earlier work knew** — `TASK_136`
measured stability within one binary; this is stability across the matrix.

⚠⚠ **NO NUMBER IN THAT TABLE IS QUOTED AS A FACT.** `p23`'s lesson holds — the
distinct-checksum count of a nondeterministic value is itself nondeterministic,
and `TASK_136` saw `18` then `20` for the same input on the same box. **The
INVARIANT is what stands and it is what `spec.md` and the gate rest on:**

> **Reading a FREED block is not reproducible; reading a RECYCLED block is.**
> The recycled read is in bounds of a live allocation whose contents the program
> itself determined, so it is stable; the freed read is glibc's business. R1h is
> stable everywhere, and every benign input is stable in every rung.

✅ **Consequence, and it is why the row is gatable at all**: gate stage 2 (every
cell prints `model.py`'s checksum) is untouched, because no benign window ever
USEs a stale record — `inputs/gen.py` refuses to write one. The adversarial rows
record behaviour per cell rather than requiring agreement, and **the row's
instrument on the UAF inputs is stage 7's `sanitizer_expect: fires`, not the
checksum.**

## 4. Eleven terms that can never fire, in every rung, and they are the proof's real price

`while (cur != NIL && live[cur] == 1 && steps < TABCAP)`, in **every** rung, plus
liveness of both children in the two-child test. Counted in
`c/kernel_hardened.c`: **six liveness conjuncts** (three walks, two in the
two-child test, one in the successor descent) and **five step bounds** (three
walks, the deletion guard, the successor descent) — **eleven terms, and not one
of them can fire.** A correct tree never links to a retired slot and no path is
longer than `TABCAP`, and the deletion loop runs at most twice.

They are here because the alternative is proving that the link structure **is a
tree** — unique parents and acyclicity — which is what *"every link points at a
live slot"* needs and which no per-slot invariant gives you. With them, the
licence for every record read is `p27`'s own per-slot `wf`
(`live[i] == 1 <==> perms.dom().contains(i)`), and the step bound is the
`decreases` measure. `controls/proof_mutants.py`'s `M7` deletes the step bound
and shows the termination proof fail.

⚠ **They are in every rung on purpose.** Putting them only in the Rust rungs
would have made every C-vs-Rust number a comparison of two different programs.
The price is that `c/kernel.c` is more defensive than a textbook BST — and that
is also the more honest bug shape: **this kernel consults `live[]` at every step
of every walk and forgets exactly once, on the one path that holds a raw
pointer.**

## 5. R4 vs R5 — `O3: norel`, `O0: differ`, and the first `differ` row in the tree

| level | R4 `unsafe.rs` | R5 `verus.rs` | verdict |
|---|---|---|---|
| `-O3 isolated` | 611 insns, `md5_raw e24fc411c686…` | 611 insns, `md5_raw 02fd34b9b2de…` | **`norel`** — `md5_raw_norel 9f816ce2e5ce…` on **both**, and `asm.py diff` reports *"normalised text identical"* |
| `-O0 isolated` | **870** insns, `d3f7c50666a8…` | **900** insns, `1316bb4ee442…` | **`differ`** |
| `-O0`, R4 respelled with `core::ptr::write` | **886** insns | 900 | still `differ` — measured, not shipped |

**At `-O3` the normalised text is identical and only pc-relative fields
differ** — the crate names differ in length, so the GOT displacements for
`__rust_alloc`/`__rust_dealloc` differ. That is link layout and not codegen,
which is what `norel` means; `p36` already ships at that level.

**At `-O0` they genuinely differ, and the reason is a p27 result that does not
transfer.** `p27` bought `-O0` identity with one line: writing `*base = v`
rather than `core::ptr::write(base, v)`, because vstd's `ptr_mut_write` is
`#[inline(always)]` over a precompiled vstd and inlines to a bare store while
`core::ptr::write` is only `#[inline]` and survives as a call. **Once the record
is a four-byte struct rather than a byte, no R4 spelling matches**: three were
built and counted, and none is 900.

⚠⚠ **`.memory/02-bench-rules.md` records that `differ` is a legal `identity`
pin that NO PATTERN HAD EXERCISED — *"one real run is owed before this is
treated as settled"*. This is that run.** The gate's consequence is the right
one: `check_miri` treats R4 ≠ R5 as a *reason Miri is required*, with Miri as the
compensating control, rather than as an error. Miri is required here anyway.

### 6b. TCB: seven items, and the second conjunct costs none of them

`buf_get_unchecked`, `arr_get_unchecked`, `arr_set_unchecked`, `rec_alloc`,
`rec_free`, `load_input`, `emit` — **the same seven `p27` ships.** Five are the
spatial accessors and the I/O every pattern here has; two are
`vstd::raw_ptr::allocate`/`deallocate` copied into the crate for a **codegen**
reason, with **vstd's own API as their verified twins**, which is what makes
them a relocation of trust rather than new trust.

✅ **The occupant-identity obligation adds nothing to the TCB.** It is
discharged by the functional postcondition — an ordinary value equality — and
not by an axiom. That is the sentence worth carrying: **the new half of `p29`'s
safety line is free in trust and expensive in proof.**

⚠ **One declaration `p27` does not need**: `global layout Rec is size == 4,
align == 1;`. `p27`'s record is a `u8` whose layout vstd axiomatises; `p29`'s is
a four-byte `#[repr(C)]` struct, because the tree's links live inside it, and
Verus gets no layout information from `#[repr(C)]`. The directive exports the
axioms **and emits a static check at codegen**, so it is checked by the compiler
on this platform rather than assumed — but it is still an axiom for the
verifier, and it is counted as one here.

### 6c. ⚠⚠ THE ORDER OF THE TWO CONJUNCTS IS FORCED AT R5

In C the safety line is one `if` with `&&`, and the short-circuit is what keeps
the identity test from being a use-after-free. **At R5 the identity test cannot
be written first at all**: reading the record needs
`perms.tracked_borrow(g_slot)`, whose precondition is
`self.dom().contains(g_slot)`, and the only thing that discharges it is
`live[g_slot] == 1`. So the C rung's `&&` ordering — a convention a reviewer
could have called style — is a **type-system consequence** one rung up. That is
why `unsafe.rs` and `verus.rs` spell the line as a nested `if` and the C rungs
spell it as one condition, and why `spec.md` pins the two spellings separately.

### 6d. What the proof looked like, so the next temporal row does not re-derive it

- **`walk` is a verified helper with a refinement `ensures`**, shared by INSERT,
  FIND and REMOVE, so the loop-invariant work happens once instead of three
  times. Its `ensures` is `r == descend(st, st.root, NIL, false, k, TABCAP)` —
  the standard *"fuel remaining"* shape, `descend(.., TABCAP - steps) ==
  descend(.., TABCAP)` as the invariant.
- **`wf` is split into `base` (read side) and the dealloc/cache conjuncts**, so
  `walk` — which frees nothing — requires only the half it needs.
- **The friction was entirely in re-establishing quantified facts after a ghost
  state update.** Verus does not carry `forall j. lv[j] ==> rec_ok(.., st, ..)`
  across `st = St { root: ch, ..st }` for free, even though `rec_ok` does not
  mention `root`; every arm needs an explicit `assert forall .. by { assert(..
  old ..) }`. That is nine short proof blocks and it is the bulk of the ghost
  code.
- ⚠ **`ensures` on a `&mut` parameter needs `final(..)`** at this Verus pin, not
  a bare mention (`../LearnVeri/PITFALLS.md` shape).
- ⚠ **`ptr_mut_from_data` is a `spec fn`.** An exec `*mut u8` → `*mut Rec`
  conversion is an ordinary `as` cast, which Verus translates through
  `spec_cast_ptr_to_thin_ptr`.

### 6e. The mutation battery, including the attack arm the rule requires

owes an ATTACK arm that must FAIL to verify, not just a deletion arm."*

## 8. What was NOT done, and what I am unsure of

- **No cost axis is published.** No rung-to-rung difference is quoted anywhere
  in this file or in `spec.md`, deliberately: the row's result is the safety
  line, and `.memory/02-bench-rules.md`'s count-the-levers rule would require
  searching both rungs' spellings before any such number could be honest.
  Neither side was searched. The measurement record exists and the numbers are
  in it; **nothing here reads them.**
- **The `H2`-vs-`R1h` R5 argument is an ARGUMENT.** §1a's third row says the
  write-path line would need a global existential invariant. **No `H2` R5 was
  built.** What is measured is that the shipped read-path R5 needs only the
  write-once invariant, which no operation re-establishes; that the alternative
  is worse is inference.
- **One spelling of the C kernel was searched, and one of the Verus encoding.**
  A different record layout — links in slot arrays rather than in the record —
  would make the proof smaller and would make the two-child splice a *choice*
  rather than a consequence of the algorithm; it was rejected for that reason
  and not measured.
- **The `-O0` `differ` result was not chased to its last instruction.** Three R4
  write spellings were built and counted (§5); which of the five write sites
  contributes which of the thirty instructions was not disassembled.
- ⚠ **`inputs/gen.py`'s benign invariant is enforced by the generator's own
  copy of the checked semantics**, which is the *functional* implementation and
  not `model.py` (which cannot be imported before the files exist). The two are
  the same algorithm written once each; if they ever diverge the gate would
  catch it at stage 2, but the generator's copy is not independently checked.
- **`harness/tools/composition.py` is NOT updated by this task.** Shipping p29
  moves what it derives — the pattern count and the TEMPORAL class — and the

  published-table refresh.** p29's safety line is temporal (a liveness test plus

## 9. SLB-TRUSTED-ARGUMENT sections

`harness/check.py` stage 5c-twin requires one per trusted item, for the three
things no stage of the gate can judge. p29's seven trusted items are the seven
`p27` ships, so where the argument is `p27`'s it says so — and **where it is
not, the difference is called out**, because the two patterns' `identity` pins
are at different levels and one of `p27`'s backstops is therefore weaker here.

## SLB-TRUSTED-ARGUMENT verus.rs buf_get_unchecked

**(a) Is the twin's body the right checked stand-in?** The trusted body is
`unsafe { *v.get_unchecked(i) }` on a `&[u8]`; the twin's body is `v[i]` on the
same `&[u8]`, with the same parameters and the same clause text. `v[i]` is the
*checked* form of the identical operation — `<[u8] as Index<usize>>::index`
performs the bounds test `i < v.len()` that `get_unchecked` requires the caller
to have performed — so a `requires` too weak to license the unchecked read is too
weak to license the indexed one, and Verus sees the second. There is no other
safe expression whose value is `v@[i as int]`.

**(b) Is the `ensures` complete with respect to every unchecked operation the
body performs?** The body performs exactly one operation, a read of one element,
and returns it. `r == v@[i as int]` names that element and its value. There is no
second read, no write, no aliasing and no interior mutability: `v` is `&[u8]`, so
the item cannot modify anything, and `u8` has no padding or niche that could make
*"the value read"* ambiguous. The completeness question TASK_009_REVIEW raises —
a body that *also* reads `i + 1` — would be invisible to this contract, and that
is why Miri is mandatory here and runs over `unsafe.rs`, which contains the same
expression inline.

**(c) Does each clause mean the same in both configurations?** One `requires` and
one `ensures`, both in terms of `v@`, `i` and `r` only; none is
`#[cfg]`-dependent, none mentions a constant `slb_twin` could redefine, and
`harness/check.py` separately rejects the token `slb_twin` anywhere except in a
twin's own attribute.

## SLB-TRUSTED-ARGUMENT verus.rs arr_get_unchecked

**(a) Is the twin's body the right checked stand-in?** The trusted body is
`unsafe { *v.get_unchecked(i) }` on a `&[T; N]`; the twin's is `v[i]` on the same
`&[T; N]`, same parameters, same clause text. For a fixed-size array `v[i]` is
the checked form of the identical operation — rustc emits the bounds test
`i < N` that `get_unchecked` requires of the caller — so a `requires` too weak to
license the unchecked read is too weak to license the indexed one. **It is
generic over `T: Copy` and `N` on purpose**: the pointer table
`[*mut Rec; TABCAP]` and the liveness array `[u8; TABCAP]` are the same operation
on two element types, and one item is one axiom instead of two. Genericity does
not weaken the argument, because the body is `T`-independent and `vstd::array`'s
`array_len_matches_n` supplies `v@.len() == N` for every `N`.

**(b) Is the `ensures` complete?** The body performs exactly one operation, a
read of one element, and returns it; `r == v@[i as int]` names that element and
its value. `v` is `&[T; N]`, so nothing can be modified. **For `T = *mut Rec` the
value is a POINTER, and "the value read" means the pointer's address *and* its
provenance** — `PtrData` carries both and `Seq<*mut Rec>` equality is equality of
both, so the clause is complete in the sense the permission map needs: the
invariant `perms[j].ptr() == tab[j]` would not survive a body that returned a
pointer with the same address and a different provenance. ⚠ **p29 leans on this
harder than `p27` does**, because `wf`'s last conjunct is
`st.gh ==> g_saved == tab[st.gs as int]` — a pointer equality between a value
this item returned at FIND time and the same slot's entry many operations later.
A body that returned an address-equal, provenance-different pointer would break
that invariant and Verus would notice; a body that read `i + 1` would not, which
is Miri's job.

**(c) Does each clause mean the same in both configurations?** One `requires`,
one `ensures`, both in terms of `v@`, `i` and `r` only; none `#[cfg]`-dependent,
none mentioning a constant `slb_twin` could redefine. `TABCAP` appears in the
call sites' types and not in this item's clauses.

## SLB-TRUSTED-ARGUMENT verus.rs arr_set_unchecked

**(a) Is the twin's body the right checked stand-in?** The trusted body is
`unsafe { *v.get_unchecked_mut(i) = x; }`; the twin's is `v[i] = x`, the checked
form of the identical store, with the same parameters and the same clause text.
Weaken the shared `requires` and Verus rejects the indexed store.

**(b) Is the `ensures` complete?** This is the harder of the two and the answer
is the whole-sequence form: `final(v)@ == old(v)@.update(i as int, x)` says both
*"slot `i` became `x`"* and *"nothing else moved"*. A trusted body that also
wrote `i + 1` would violate the second half and Verus would reject it **if it
could see the body** — it cannot, which is TASK_009_REVIEW's x4 exactly and
exactly why `miri.required` is `true` here and runs over `unsafe.rs`, which
performs the same store inline. There is no read, so there is nothing else to
state. **`x` is a pure VALUE parameter** — stored, never used as an address, an
index or a length — so it carries no precondition; that is the
parameter-coverage false positive `.memory/04-verus.md` names, `spec.md`'s
`verus.unsafe_justifications` declares it, and the gate shouts it every run.
⚠ **On p29 this item is what clears the liveness bit**
(`arr_set_unchecked(&mut live, cur as usize, 0u8)`), i.e. it is the item the
whole temporal invariant is re-established through; the *"nothing else moved"*
half is what makes `wf`'s `lv[j] <==> live[j] == 1` survive a deletion.

**(c) Does each clause mean the same in both configurations?** `old(v)@`,
`final(v)@`, `i` and `x` only; no `#[cfg]`, no redefinable constant.

## SLB-TRUSTED-ARGUMENT verus.rs rec_alloc

**(a) Is the twin's body the right checked stand-in?** **The twin's body is
`allocate(size, align)` — `vstd::raw_ptr::allocate` itself**, which is the
strongest stand-in available anywhere in this project: the checked
implementation of the trusted item is the very API the item is a copy of, so
what stage 5c-twin proves is that this crate's contract is **no stronger than the
one vstd already discharges**. If any `requires` here were weaker than vstd's, or
any `ensures` stronger, the twin would not verify. `p27`'s NOTES 10 records the
four-way clean negative against the obvious circularity attack — weakening the
contract *and* its twin together is caught in the `--cfg slb_twin` run, and a
one-sided weakening is caught by the gate's structural signature-identity rule —
and that argument is about the mechanism, not about `p27`, so it transfers
unchanged.

⚠⚠ **ONE OF `p27`'s TWO BACKSTOPS IS WEAKER HERE AND THE DIFFERENCE MUST NOT BE
GLOSSED.** `p27` closes the body-drift gap (the twin cannot see the item's
*body*, which is a copy of vstd's rather than a call to it) with (i) `md5_raw` of
`unsafe::kernel` and `verus::kernel` equal at `-O3 isolated`, so R5's inlined
body **is** R4's byte for byte, and (ii) Miri over `unsafe.rs`. **On p29 leg (i)
is `md5_raw_norel`, not `md5_raw`** (§5): the normalised instruction text is
identical and only pc-relative displacement fields differ, which is link layout
rather than codegen — so the claim *"R5's inlined body is R4's"* still holds at
the instruction level but is certified one notch weaker. **And at `-O0` the pair
is `differ` outright**, so leg (i) says nothing there at all. ✅ **Leg (ii) is
unchanged and is the independent one**: Miri runs over `unsafe.rs`, which
contains this body.

The item exists for **codegen and not for trust**: vstd carries no `#[inline]` on
`allocate`, so calling it emits a GOT-indirect cross-crate call that `unsafe.rs`
cannot produce.

**(b) Is the `ensures` complete with respect to every unchecked operation the
body performs?** The body performs one operation — `std::alloc::alloc(layout)`
after `Layout::from_size_align_unchecked(size, align)`, aborting on null — and
returns the pointer plus two tracked permissions. The three clauses state exactly
what a caller may conclude: the `PointsToRaw` covers `[addr, addr+size)`, the
`Dealloc` records the address, size, align and provenance the eventual `rec_free`
must match, and the returned pointer's provenance is the `PointsToRaw`'s. **Three
clauses, and `spec.md`'s `verus.items` dump lists three.** Two further clauses
exist in vstd and are deliberately NOT shipped — `addr + size <= usize::MAX + 1`
and `addr % align == 0` — because this kernel allocates at `align == 1`, where
the second is a tautology and the first is never used; dropping them makes the
item strictly weaker and the twin still verifies, which is the direction the gate
asks for. The `requires` is vstd's own and the `size != 0` conjunct is not a
tautology (`RECSZ` is 4, but the item is generic in `size`).

**(c) Does each clause mean the same in both configurations?** Every clause is in
terms of `size`, `align` and the return binding `pt` only, and all three of
`PointsToRaw::is_range`, `Dealloc::view` and `DeallocData` are vstd items that
`slb_twin` cannot redefine. The shipped item and the twin sit in the same module
with the same imports and the same `opens_invariants none`, and their signatures
are character-identical after normalisation — which the gate checks.

## SLB-TRUSTED-ARGUMENT verus.rs rec_free

**(a) Is the twin's body the right checked stand-in?** **The twin's body is
`deallocate(p, size, align, pt, dealloc)` — `vstd::raw_ptr::deallocate`
itself**, for the same reason and with the same force as `rec_alloc`: the gate
proves this crate's copy is no stronger than vstd's original. Same codegen
motivation, and the same weakened leg (i) disclosed above.

**(b) Is the `ensures` complete?** There is no `ensures`, and that is correct
rather than lazy: the item's whole semantic content is that it **consumes** the
`PointsToRaw` and the `Dealloc`. Linearity is the postcondition. A caller that
has given up slot `cur`'s permission cannot later present it to `rec_read`.
⚠⚠ **AND ON p29 THAT IS ONLY HALF OF THE PROPERTY, WHICH IS THE WHOLE POINT OF
THE ROW.** The two-child splice calls this item on the **successor** and not on
the victim, so the victim's permission survives, a stale read of the victim is
perfectly provable, and nothing about this item's contract objects. What rejects
that read is the kernel's **functional** postcondition, not linearity —
`controls/proof_mutants.py`'s `M3` is the measurement. The `requires` is vstd's
own, six conjuncts, and covers every parameter: `p`, `size` and `align` through
the four `dealloc@.*` equalities, and both permissions through
`pt@.is_range(..)` and the provenance equality. **The body performs one
operation**, `std::alloc::dealloc(p, layout)`.

⚠ **What a wrong body here would do and what would catch it.** A body that
deallocated a *different* pointer, or that did nothing at all, would satisfy this
contract — there is nothing to satisfy. Nothing in Verus can catch it; **Miri
can**, and does, over `unsafe.rs`'s identical `rec_free`: a leak or a mismatched
free is a Miri error, and `miri.required` is `true` for exactly this reason. This
is `.memory/04-verus.md`'s point that an `external_body` `ensures` is an axiom
about a body no verifier reads.

**(c) Does each clause mean the same in both configurations?** Every conjunct is
in terms of `p`, `size`, `align`, `pt@` and `dealloc@` only; `Dealloc::addr`,
`size`, `align`, `provenance` and `PointsToRaw::is_range`/`provenance` are vstd
items `slb_twin` cannot redefine. Both items sit in the same module with the same
imports and the same `opens_invariants none`.

## SLB-TRUSTED-ARGUMENT verus.rs load_input

**(a)** There is no twin and there cannot be one: the item is plain Rust I/O
(`driver::arg_path`, `driver::load`, `driver::head1_u64_bytes`) with **no
`unsafe` in its body and no `ensures`**, so it is outside the twin regime that
stage 5c-twin checks. It is `external_body` because Verus cannot type
`std::fs`, not because anything unchecked happens.

**(b)** There is nothing to be complete about: no clause is stated, so the item
licenses nothing. Every fact the kernel needs about `buf` is re-derived from
`buf@` at the call site.

**(c)** No clause, so no configuration-dependence. Every pattern in this tree
ships the same pair of I/O items for the same reason.

## SLB-TRUSTED-ARGUMENT verus.rs emit

**(a)**, **(b)**, **(c)** as for `load_input`: plain `println!` behind an
`external_body` wrapper because Verus cannot type `core::fmt`, no `unsafe`, no
clauses, no twin, nothing licensed.
