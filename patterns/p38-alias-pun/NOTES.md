# p38 — strict aliasing / type punning: working notes

Contract and pins: `spec.md` (generated by `controls/mkcontract.py`).
Numbers: `results/p38-alias-pun.json` and `results/tables/p38-alias-pun.md`.
Gate: `harness/check.py p38`.

**The one-line result.** p38 is the first bug class in this tree that **unsafe
Rust does not reintroduce**, because Rust has no type-based aliasing rule for
`unsafe` to unlock. On the C side the *check is written* and the compiler is
entitled to ignore it: gcc 13.3.0 at `-O2`/`-O3` answers a `uint32_t` re-read of
a length field from before the `uint16_t` clamp that narrowed it, and the stale
attacker-controlled length then bounds a fold that reads off the end of the
scratch. clang 22.1.6 does not — **and the reason is a mechanism, not a version
number** (§0d).

---

## 0. §0 — the bug class and the harm, settled before any rung was written

### 0a. The catalogue's own spelling is the BENIGN direction — confirmed

`.memory/06-catalogue.md:400` describes p38 as *"endian conversion / type
punning (`memcpy` vs union)"*, i.e. reading a `uint32_t` out of an
`unsigned char` array. That is UB by C99 6.5p7 and **neither compiler exploits
it**. Re-derived independently of the manager's probe (`.temp/p38probe/bytebuf.c`
run under my own harness, 16 cells = {gcc 13.3.0, clang 22.1.6} × `-O0..-O3` ×
`±-fstrict-aliasing`):

```
via_cast   = 0   in 16 of 16 cells      the defined answer, always
two_types  = 1   at -O1/-O2/-O3 with -fstrict-aliasing, BOTH compilers
           = 0   at -O0 and with -fno-strict-aliasing, both compilers
```

The manager's probe 2 is **confirmed**: the character-typed direction is benign
because both compilers key TBAA on the *access* type and a character access may
alias anything. **Only two incompatible non-character types move.** p38 is built
on that direction; a pattern built on the catalogue's spelling would have
returned a null result for the wrong reason. Fifth catalogue row overturned.

### 0b. The bounds-narrowing harm — the manager's least-certain call — REPRODUCES

TASK_066 named it: *"a clamp written through one type and read through an
incompatible one, so a stale unclamped length survives into a bounds check as a
real OOB read"*, and asked for the measurement before six rungs were built on
it. **It reproduces, in a shipped binary, as a real out-of-bounds read.** The
wrong-answer fallback is not needed and p38 is a memory-safety pattern.

Probe ladder, all in `.temp/p38/`:

| probe | shape | gcc `-O1/-O2/-O3` `-fstrict-aliasing` | clang | `-fno-strict-aliasing` |
|---|---|---|---|---|
| `harm.c` A | u16 word buffer, u32 length read | **4000** (unclamped) | 16 | 16 |
| `harm.c` B | `uint64_t` scratch, struct overlay | **4000** | 16 | 16 |
| `harm.c` C | two struct views (`v1`/`v2`) | **4000** | 16 | 16 |
| `harm.c` E | u32 halves, u64 field | **4000** | 16 | 16 |
| `harm.c` D | the textbook float/int pun | **4000** | **4000** | 0 |
| `harm.c` F | clamp written through `unsigned char` | 16 | 16 | 16 |

(`CAP` is 16, the attacker length 4000, and the defined answer is 16 in every
row but D and F.) Then `harm5.c`, a real record walker on a heap buffer:
`oob_words = 3994` on gcc `-O1/-O2/-O3`, `0` on clang and `0` under
`-fno-strict-aliasing`; **ASan reports `heap-buffer-overflow READ of size 2`**,
gcc (`-static-libasan`) and clang alike.

### 0c. What was rejected, and why

| candidate | rejected because |
|---|---|
| `uint32_t` out of an `unsigned char[]` (the catalogue's) | benign on both compilers, 16 of 16 cells — §0a |
| float/int punning of a length | weaponised on both, but **no idiomatic C parser puns a length through a `float`**; it fails the reviewer checklist's "is this Rust-in-C-syntax written to lose?" inverted |
| a **two-pass** parser (sanitise loop, then parse loop) | **does not reproduce** (`harm4.c`, 12 of 12 cells clean). TBAA weaponisation is redundant-load-elimination: it needs the aliasing store and the load in one optimisable region, with the load forwardable from an *earlier* load. Across two loops the memory really is written and the reload really happens. This is the single most useful negative here and it is what forced the accessor-pair shape. |
| a 2-word local header buffer (`harm5.c` design H) | **does not reproduce** on either compiler: SROA promotes a 2-element array to registers and the access — with it the aliasing question — stops existing |
| `-fno-strict-aliasing` as the R1h *cell* | it is a **build-flag** change and `build.py` is hashed into the measurement records (RECAP settled answer 4). Priced in `controls/` instead — §8c. **No `harness/` change was needed for p38.** |

### 0d. ⚠ WHY clang declines and gcc does not — the mechanism, not the version

`controls/gen_controls.py` ships this as `x_mustalias`. One function body, two
spellings, the same address at run time:

```
        one_base(uint32_t *lenp)               two_params(uint32_t *lenp, uint16_t *w)
        u16 view derived from the u32 pointer  two parameters the compiler cannot relate
gcc     4000 at -O1/-O2/-O3                    4000 at -O1/-O2/-O3
clang   16 (declines)                          4000 at -O1/-O2/-O3
both    16 under -fno-strict-aliasing          16 under -fno-strict-aliasing
```

**LLVM does not apply TBAA when BasicAA has already proved the two accesses are
the same address**; GCC applies it regardless. A single-base accessor pair — the
idiomatic shape, and p38's — is exactly the case BasicAA settles first. So
*"clang is safe from strict aliasing"* is **false**; the true statement is
*"clang's alias analysis answers this particular query before TBAA is
consulted"*, and a spelling one step away flips it.

### 0e. The harm ladder, and the shape it inherits

The clamp's stale length can land in three places, and only the attacker's
declared `rlen` decides which. `adversarial-stale` is p17's shape exactly
(inside the object, every instrument silent); `adversarial-oob` is the one that
leaves it. See §5 and §6.

## 1. Does the UB spelling buy anything? — the static answer, and it is not the expected one

`harness/asm.py stat`, `-O3`, `isolated`, symbol `kernel`:

| `rec_len` spelling | defined? | gcc `n_fn_nopad` | gcc `md5_fn` | clang `n_fn_nopad` | clang `md5_fn` |
|---|---|---:|---|---:|---|
| `*(const uint32_t *)r` (**R1**, the pun) | **no** | 237 | `096a44a91938…` | 175 | `366e3be50428…` |
| `(uint32_t)r[0] + 65536 * (uint32_t)r[1]` (**R1h**) | yes | 243 | `c8c254603fa0…` | 185 | `b95b356fa703…` |
| `memcpy(&v, r, 4)` (`c_memcpy`) | yes | 236 | `b468b6f05c6f…` | **175** | **`366e3be50428…`** |
| the union (`c_union`) | yes | 236 | `b468b6f05c6f…` | **175** | **`366e3be50428…`** |
| the pun, `-fno-strict-aliasing` (`c_nosa`) | yes | 236 | `bd5bcdf155af…` | **175** | **`366e3be50428…`** |
| the pun with **one** `rec_len` call (`c_once`) | no | 236 | `5374e1e5e2a8…` | 172 | `04f3c0e255b9…` |

**Read the clang column first.** `c_memcpy`, `c_union` and `c_nosa` are
**byte-identical to the UB spelling** — same 175 instructions, same
`md5_fn 366e3be50428933dee85aae05655e7ff`. On clang, *"the UB buys literally
nothing"* is not a slogan, it is a digest.

**And the R1h row is the one that surprises.** The defined two-half spelling is
**+6 instructions on gcc and +10 on clang**, and the two compilers get there by
*different* routes — read off the shipped listings rather than assumed:

- **clang** (and **rustc**) *merge* the two 16-bit loads back into one 32-bit
  load and then **fail to simplify `(x & 0xffff) + 65536 * (x >> 16)` back to
  `x`**: the recomposition survives as
  `mov %r11d,%r10d ; shr $16,%r10d ; movzwl %r10w,%ebx ; shl $16,%rbx ; and $0xffff,%r11d ; or %rbx,%r11`.
  The R4 kernel's own listing has the same shape — the merged load
  `mov (%rsp,%r8,2),%r10d` followed by the same re-split — so **rustc pays
  clang's 10 in every Rust rung**.
- **gcc does not merge at all.** `c-gcc-h`'s walk head issues two separate
  zero-extending 16-bit loads and combines them by hand:
  `movzwl (%rsp,%rcx,2),%r12d ; movzwl (%rdx),%esi ; shl $16,%esi ; add %r12d,%esi`.
  That is the +6.

⚠ **So "all three compilers merge and then fail to fold" is FALSE as a single
sentence** — it is true of clang and rustc and false of gcc, and the two
mechanisms happen to cost 10 and 6.

So p38 ships **two** answers to "does the UB buy anything", and they have
different domains:

- against the **right** defined spelling (`memcpy`, or the union, or the flag):
  **zero on clang, one static instruction on gcc, −6.00 Ir/call on gcc** (§8c);
- against the spelling **the named-spelling standard forces on every rung**:
  **3.00000 Ir per record on gcc and 8.00000 on clang**, exactly (§4b).

⚠ **The shipped R1h is the two-half spelling and not `memcpy`, deliberately.**
No Rust rung can write the merged load — `read_unaligned` is inadmissible at the
pinned vstd (§8b) — so a C hardened rung that used `memcpy` would put a codegen
difference no Rust rung can have into p38's safety column.

## 2. The bug on the SHIPPED binary — disassembled, not inferred

p13's lesson is that a text pin binds the source and not the object, and p38 is
the pattern where that is the whole subject. The claim is therefore made about
`.temp/build/p38/c-gcc-O3-isolated`.

The record-walk head of `c-gcc-O3-isolated`, `harness/asm.py show --sym kernel`,
instructions 198-209 of the kernel (immediates and branch targets normalised
away by `asm.py`, as always):

```
mov    %rbp,%rcx                 ; nw
lea    (%rbx,%rdx,2),%rsi        ; &sc[i]
mov    (%rsi),%r12d              ; <<< rec_len: ONE 32-bit load of sc[i],sc[i+1]
sub    %rdx,%rcx                 ; nw - i
shr    $1,%rcx                   ; room
lea    (%r12,%r12,1),%rdi        ; <<< 2*n, FROM THE PRE-CLAMP VALUE
cmp    %r12,%rcx                 ; the clamp's test
jae    TGT                       ; not over-long -> skip the clamp
mov    %cx,(%rsp,%rdx,2)         ; THE CLAMP STORE, low half
xor    %edx,%edx
mov    %dx,(%rsi)                ; THE CLAMP STORE, high half
```

**The fold's trip count `%rdi` is computed at the third instruction, from the
value loaded before the stores, and there is no second load of `sc[i]` anywhere
in the shipped gcc kernel.** The clamp's two stores are emitted and executed and
never observed. That is the miscompilation, on the object, at the address the
driver calls.

`c/kernel_hardened.c` at the same optimisation level **reloads**, in the same
place — instructions 198-213 of `c-gcc-h-O3-isolated`:

```
movzwl (%rsp,%rcx,2),%r12d       ; rec_len, low half
movzwl (%rdx),%esi               ; rec_len, high half
...
cmp    %rsi,%rbp                 ; the clamp's test
jae    TGT
xor    %esi,%esi
mov    %bp,(%rsp,%rcx,2)         ; THE CLAMP STORE, low half
mov    %si,(%rdx)                ; THE CLAMP STORE, high half
movzwl (%rsp,%rcx,2),%esi        ; <<< THE RE-READ, after the stores
add    %rsi,%rsi                 ; <<< 2*n, from the CLAMPED value
```

So does `c-clang`. So does every Rust rung.

**Behaviour, all 16 C cells, on `adversarial-oob.bin`** (defined answer
`8516071857945885891`):

| cell | `O0` isolated | `O0` whole | `O3` isolated | `O3` whole |
|---|---|---|---|---|
| `c-gcc` | defined | defined | **wrong, and not reproducible across runs** | **wrong, and not reproducible** |
| `c-clang` | defined | defined | defined | defined |
| `c-gcc-h` / `c-clang-h` | defined | defined | defined | defined |

The wrong value differs from run to run because what the fold reads past `sc` is
stack residue under ASLR — p03's pointer-disclosure shape, not p02's
deterministic corruption. Five consecutive runs of `c-gcc-O3-isolated` on the
probe blob gave five different checksums.

## 3. Anti-collapse

`collapse.probe_inputs` are `small.bin` (`work_per_call` 200 window bytes) and
`large.bin` (516). `model.py` declares no `min_ir_per_work`, so the harness

margin as if it were evidence for something.

### 4b. Two exact laws, fitted on two bands and tested OUT OF SAMPLE

`controls/fit.py`, over `inputs/gen.py --sweep`. `nrec` varies alone in band
`sweep-r*` (10 blobs), `rlen` alone in band `sweep-w*` (12 blobs), and band
`sweep-x*` (6 blobs) holds pairs **neither band contains**, so the model is
*predicted* there rather than re-fitted. Every figure is a matched-spelling
difference between two cells on the same blob, so the driver constant, the
decode loop and the payload fold cancel exactly.

```
R1h - R1  =  3.00000 * nrec     (gcc)    22 fit blobs, max residual 0.00000
                                          6 out-of-sample, max residual 0.00000
R1h - R1  =  8.00000 * nrec     (clang)  22 fit blobs, max residual 0.00000
                                          6 out-of-sample, max residual 0.00000
```

Independent of `rlen` over 1…60 — the price is **per record**, not per byte,
because it is the recomposition of one length field. It predicts the measured
matrix without being fitted to it: `small` has `nrec` 4 → +12.0 (gcc) / +32.0
(clang) and `large` has `nrec` 8 → +24.0 / +64.0, which is exactly §4a.

```
R3 - R4   =  17 + 1.00 * nrec            exact on 27 of 28 sweep blobs
                                          and on BOTH measured blobs
```

`small` → 17+4 = **21** ✓, `large` → 17+8 = **25** ✓, and all six out-of-sample
`sweep-x*` blobs hit it to 0.00. ⚠ **The one exception is named rather than
smoothed:** `sweep-w01.bin` (`rlen` 1, i.e. a two-word payload) measures **21**
where the law says 19. At that size the reslice's setup has nothing to amortise
over. Every other blob, including `rlen` 60, is exact.

**So p38's safety tax is `O(1)` per record and 0.00 per payload byte** — the
reslice sits outside the fold, which is p16's mechanism a fourth time.

### 4c. ⚠ The additivity test FAILED for `R2 − R4`, and that is worth more than the two passes

```
R2 - R4   fitted d = 61.20 - 6.66*nrec + 6.42*nrec*rlen
          max in-sample residual  27.41
          max OUT-OF-SAMPLE residual  86.66   (sweep-x09u03: 88 measured, 175 predicted)
```

The two-regressor model is **wrong** for R2, and the mechanism is identifiable
rather than a shrug: R2 also pays a bounds check **per window byte in the decode
loop**, and `nw` is a third structural parameter that neither band varies (240,
244 and 256 across the three bands). The law is not "R2 is noisy"; it is "the
model is missing a regressor, and the out-of-sample test is what said so". This
is the first time this project's additivity test has failed, and it failed on
the one pair whose regressor set was incomplete while passing on the two whose
set was complete.

### 4d. Wall clock

Secondary, and 6 of 32 O3 wall cells exceeded the 10% min-to-median spread and
are discarded by `harness/measure.py` (marked ✗ in
`results/tables/p38-alias-pun.md`). **No claim above rests on a wall-clock row.**
p38's per-call `Ir` differences are 0.4%–4% of the kernel, which is inside this
box's layout band for several rungs (`.memory/05-layout.md`), so the honest
statement is that the `ns` column neither confirms nor contradicts §4a.

## 5. Adversarial rows, per rung

`harness/check.py` stage 4 records these; the table below is the reading.

| input | `rlen` declared | what the defined semantics does | `c-gcc` `O3` | `c-clang` `O3`, both C rungs at `O0`, both `-h` cells, and **all four Rust rungs at every cell** |
|---|---|---|---|---|
| `adversarial-stale` | 60 units (120 words) | clamps to 48 units | reads scratch words 2…122 — **inside** the 256-word array but past the 98 the decode loop wrote; wrong, silent, not reproducible | model checksum |
| `adversarial-oob` | 200 units (400 words) | clamps to 48 units | reads **past** `sc[256]` into the frame; wrong, silent, not reproducible | model checksum |
| `adversarial-huge` | 0xFFFFFFF units | clamps to 48 units | **SIGSEGV** | model checksum |
| `adversarial-nrec` | well formed, `nrec` = 0xFFFFFFFF | the `i + 2 <= nw` guard stops the walk | model checksum | model checksum |
| `adversarial-stride7` | — | the driver's `stride_w >= 8` guard skips the loop | `0` | `0` |

**Four of the eight cells are immune, and four columns saying so IS the
finding.** R2, R3, R4 and R5 print the model's checksum on every adversarial
input at every optimisation level and inline mode. None of them is immune
because of a check: delete every bounds check from R4 (which is what R4 *is* —
`get_unchecked` throughout) and it is still immune, because the property that
protects it is that a `u16` store is observed by a later `u16` load, which is
the language and not a runtime test.

**What an adversarial row *means* when the harm is a miscompilation.** On every
other pattern here the adversarial input makes the *program* do something wrong.
Here the input makes the *compiler* do something wrong, and the same source
compiled one optimisation level lower is correct on the same input. That is why
the row is a per-(cell, opt, mode) table and not a per-rung one, and why the
`c-gcc` cells legitimately disagree with each other: `O0` clamps, `O3` does not.

### 6a. ⚠ TySan's blind spot is PROMOTION, not inlining — the manager's probe 4 corrected

The manager's probe 4 reported *"TySan's blind spot is INLINING, not
optimisation level"* and flagged that it might be SROA. **Re-derived on my own
sources, the correlation holds and the causal factor is promotability.**

Reproduction of the manager's table (my `ty_main.c`+`ty_lib.c` vs
`ty_single.c`, violations reported):

| | `-O0` | `-O1` | `-O2` | `-O3` |
|---|---|---|---|---|
| two TUs (not inlined) | 2 | 2 | 2 | 2 |
| one TU, `static` (inlined) | 2 | **0** | **0** | **0** |

Three mechanism probes that separate the two candidates:

| probe | shape | `-O0` | `-O1` | `-O2` | `-O3` |
|---|---|---|---|---|---|
| `M1` | one TU, `static` + **`noinline`** | 2 | 2 | 2 | 2 |
| `M2` | one TU, inlined, object on the **heap** | 2 | 2 | 1 | 1 |
| `M3` | one TU, inlined, stack object whose **address escapes** to an opaque callee | 2 | 2 | 2 | 2 |

`M1` shows "one TU" is not the discriminator — **inlining is necessary**. `M2`
and `M3` show it is not sufficient: keep the object in memory and TySan fires at
every level even fully inlined. **The blind spot is SROA/mem2reg promoting the
object out of memory; inlining matters only because a cross-TU call forces the
object into memory in the first place.**

**And that predicts p38, which is the test that could have failed.** p38's
scratch is a real 512-byte in-memory array, so promotion cannot happen, so TySan
should fire in *both* inline modes. It does:

```
clang -O3 -fsanitize=type -DSLB_ISOLATED   ERROR: TypeSanitizer: type-aliasing-violation
clang -O3 -fsanitize=type -flto            ERROR: TypeSanitizer: type-aliasing-violation
```

So **p38 is NOT the pattern where the catcher has an inline-mode domain**, and
the reason it is not is the same measurement that explains why the manager's toy
did. That is the correction: the domain is *promotable object*, and `isolated`
vs `whole` is a proxy for it that happens to be exact on a two-line function and
inexact on a real one.

## 7. The trusted base

**Five** `external_body` items, **three** with contracts. Recount from
`verus.rs`: `buf_get_unchecked`, `sc_get_unchecked`, `sc_set_unchecked`,
`load_input`, `emit`. Classification: **3 U-license + 2 infra + 0 V-gap**.
p03's shape and for p03's structural reason — two buffers, one of them written.
`spec.md`'s `verus.items` pins all five plus the three
`slb_twin_*` twins; the gate's `tcb_items` must equal 5.

`verus.rs` = 13 verified / 0 errors; `--cfg slb_twin` = 16 / 0. The +3 is one
per twinned item.

### SLB-TRUSTED-ARGUMENT verus.rs buf_get_unchecked

(a) *Is the twin's body the right checked stand-in?* The trusted body is
`unsafe { *v.get_unchecked(i) }` and the twin's is `v[i]`. vstd specifies the
checked slice index with the obligation `i < v@.len()`, which is this item's
`requires` verbatim, so a `requires` too weak to license the unchecked read is
too weak to license the checked one and Verus rejects the twin. The gate's
5c-twin per-conjunct deletion confirms the twin *uses* the clause.

(b) *Is the `ensures` complete with respect to every unchecked operation the
body performs?* The body performs exactly one — a byte read at `i` — and the
single `ensures` `r == v@[i as int]` determines its value. The known blind spot
applies and is not closed here: a body that *also* read `i + 1` would satisfy
this contract, so the argument rests on the body being three tokens long and
visible in the same file. Miri on `unsafe.rs` is the backstop and
`miri.required` is true.

(c) *Does each clause mean the same in both configurations?* Yes. The signature,
the `requires` and the `ensures` are character-identical between the shipped
item and `slb_twin_buf_get_unchecked`; `#[cfg(slb_twin)]` is a cfg no measured
build sets, so the twin is stripped before codegen and the shipped object is
unaffected.

⚠ **On p38 this item's `requires` has nothing to do with the pattern's bug.**
It bounds a read of the *input window*, and `c/kernel.c` gets every window read
right. The item is here because the R4 rung reads the window unchecked, not
because p38's harm is a window overrun.

### SLB-TRUSTED-ARGUMENT verus.rs sc_get_unchecked

(a) *Is the twin's body the right checked stand-in?* Trusted body
`unsafe { *v.get_unchecked(i) }` on a `&[u16; 256]`; twin body `v[i]`. vstd's
array index carries the same `0 <= i < N` obligation, and `array_len_matches_n`
supplies `v@.len() == 256` from the parameter type, so the twin's obligation is
this item's `requires` and nothing else.

The `requires` is **one conjunct**, `i < v@.len()`, and deliberately **not**
`i < v@.len(), v@.len() == 256`: for a `&[u16; 256]` the second is a tautology
discharged from the parameter type alone, which demands nothing of any caller.
p03 shipped a draft with exactly that second conjunct and the gate's 5c-req
tautology probe refused it; p38 does not repeat it.

(b) *Is the `ensures` complete?* One unchecked operation, one clause determining
its value. Same blind spot, same backstop. **This item is where p38's harm would
land** — a stale `n` makes `i + 2 + k` exceed 256 — and it is the obligation
`controls/proof_mutants.py`'s `m_clamp_off` and `m_no_trunc` both break (§9).

(c) *Same meaning in both configurations?* Yes, character-identical signature and
clauses; `#[cfg(slb_twin)]` only.

### SLB-TRUSTED-ARGUMENT verus.rs sc_set_unchecked

(a) *Is the twin's body the right checked stand-in?* Trusted body
`unsafe { *v.get_unchecked_mut(i) = x; }`; twin body `v[i] = x;`. Verus
specifies the checked indexed store on an array with the same bound, so
weakening the shared `requires` makes the twin fail. This is the project's
second trusted item that **writes** through an unchecked index (p03's is the
first).

(b) *Is the `ensures` complete?* The `requires` is one conjunct,
`i < old(v)@.len()`. The body performs exactly one unchecked operation, a store
of `x` into slot `i`, and the single `ensures` is a **whole-sequence equality**,
`final(v)@ == old(v)@.update(i as int, x)` — so it says both *"slot `i` became
`x`"* and *"nothing else moved"*, and a body that also wrote `i + 1` would
contradict it rather than slip past it. For a **write** whose result the
`ensures` fully determines the usual blind spot is narrower than for a read; it
is not closed, because a write *outside* `v` would still be invisible, and Miri
is why `miri.required` is true.

`x` is a pure **value** parameter — written, never used as an address or a
length — so it carries no precondition, and `spec.md`'s
`verus.unsafe_justifications["verus.rs"]["sc_set_unchecked"]` declares that and
the gate shouts it every run. `.memory/04-verus.md` names this false positive of
the parameter-coverage rule; p03 was the first pattern to exercise it and p38 is
the second.

(c) *Same meaning in both configurations?* Yes.

⚠ **AND THIS IS WHERE THE LANGUAGE DIFFERENCE LIVES.** The `ensures` says the
store lands and is subsequently observable. The corresponding C statement is
`r[0] = (uint16_t)(v % 65536)`, and in C a later read of the same storage
through a `uint32_t` lvalue need **not** observe it — which is p38's entire bug.
That the Rust one is observed is not an axiom about this wrapper: it is Rust's
memory model, which has no type-based aliasing rule for the axiom to be wrong
about. **If Rust had C's rule, this `ensures` would be unsound and nothing in
this gate would notice.**

### 8c. The flag price — and it is negative

No pattern in this tree had priced a whole-program-semantics flag.
`controls/gen_controls.py`'s `c_nosa` is the shipped `c/kernel.c` with one flag
added, measured in the same run as `c_pun` (whole-program marginal, `small.bin`,
`O3 isolated`):

| | `-fstrict-aliasing` (default) | `-fno-strict-aliasing` | price |
|---|---:|---:|---|
| gcc 13.3.0 | 1043.72 | 1037.72 | **−6.00 Ir/call** |
| clang 22.1.6 | 1274.72 | 1274.72 | **0.00, byte-identical** (`md5_fn 366e3be50428…`) |

**The flag that fixes the bug is free on clang and *saves* 6 instructions per
call on gcc**, because what strict aliasing bought gcc here was the deletion of
a reload that the surrounding code then had to work around. ⚠ **Domain, not a
law**: this kernel is a straight-line record walk with no loop that writes
through one type and reads through another, which is where the flag's real cost
would be. p38 prices the flag *on p38*; it does not price the Linux kernel's
build.

Two further zero-cost fixes, from §1: `c_memcpy` and `c_union` are
byte-identical to the UB spelling on clang and one instruction from it on gcc.
`c_once` — the same pun with `rec_len` called once instead of twice — is
**correct on every cell** and 6.00 Ir/call cheaper than the buggy spelling,
which is the control that shows the *re-read* is what the bug needs.

## 9. What the proof says, and what it cannot

`verus.rs`: **13 verified, 0 errors**, first run, no lemma beyond the driver's
existing nonlinear block. Decomposition, each term measured with
`--verify-function <name> --verify-root`: `SCRATCH_W` 1 + `wfold` 1 + `rwalk` 1
+ `kernel` 5 + `main` 5 = 13. `kernel`'s 5 is one body query, one per loop body
(decode, record walk, payload fold) and one for the single
`assert … by (nonlinear_arith)`.

**Every obligation in the file is SPATIAL.** What R5 buys on p38 is that the
three unchecked reads and the one unchecked write stay inside their objects.
`controls/proof_mutants.py` shows both directions of that:

```
m_clamp_off   12 verified, 1 errors   REJECTED   invariant not satisfied before loop
              `if d > room` -> `if d > room + 1` (and the ghost step it invalidates)
m_no_trunc    12 verified, 1 errors   REJECTED   invariant not satisfied before loop
              delete `if nw > SCRATCH_W { nw = SCRATCH_W; }`
```

Both fail on the payload fold's `i + 2 + 2 * n <= nw` — the spatial fact — and
not on a ghost assertion. (The `m_clamp_off` mutant deletes `assert(n <= room)`
with the clamp edit, deliberately: that assertion is a *step* in the proof of
the bound, and leaving it in makes the mutant fail on `assertion failed`, which
would not tell a reader whether memory safety was ever at risk.)

**And what it cannot say — the deliverable, not the gap.** There is no mutant
of `verus.rs` corresponding to p38's own defect, because there is no way to
write p38's defect in Rust. This is p47's shape one axis over, and the *reason*
differs, which is the part worth stating precisely:

- **p47**: the property (constant time) is **inexpressible** — Verus's assertion
  language has no term denoting a trace.
- **p38**: the property is **vacuous in the language the proof is about**.
  Strict aliasing is a rule of the *C* abstract machine. `verus.rs` is a Rust
  program; Rust's `&mut` carries `noalias`, which is **uniqueness** — a
  provenance property — and no reference or raw pointer in Rust carries a type
  tag an optimiser may reason from. There is no obligation for Verus to fail to
  discharge.

The honest sentence: **R5 proves the Rust program memory-safe and says nothing
whatever about the C program that shares its algorithm — and the C program's
defect is invisible to every oracle in this repository except a disassembly, an
instruction count, and TySan.** `sc_set_unchecked`'s `ensures` is the exact
place where the assumption lives (§7), and it is an assumption about the
*language*, not about the wrapper.
