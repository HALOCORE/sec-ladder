# p12 — `strcat` into a fixed buffer: findings

Read `spec.md` first; it is the contract and this file is what was measured
against it. Every number here is reproducible from the committed tree — the
`.bin` inputs are gitignored and regenerated by `inputs/gen.py`, the controls by
`controls/gen_controls.py`.

## 0. What the bug does at the gate's own flags — and it is three answers, not one

**The premise this pattern was commissioned on was that R1 might just abort.** It
does not, or rather it does only in one of three regimes, and which regime you
are in is decided by **how far past the array the copy goes** and by **which
compiler built the cell**.

`harness/build.py`'s C flags are `-std=c99 -Wall -Wextra -O0|-O3` plus
`-DSLB_ISOLATED` or `-flto`. **No `-fstack-prot*` flag is passed either way**, so
each compiler's default decides, and the two defaults differ:

```
$ /usr/bin/gcc -Q --help=common | grep stack-protector
  -fstack-protector                     [disabled]
  -fstack-protector-all                 [disabled]
  -fstack-protector-explicit            [disabled]
  -fstack-protector-strong              [enabled]
$ ~/tools/llvm/bin/clang -### -c x.c 2>&1 | tr ' ' '\n' | grep -i stack-prot
  (nothing)
```

Measured on `.temp/p12/probe_sp3.c` — one string of length `T` copied into
`uint8_t dst[128]` with no capacity check, `-O3`:

| bytes copied | overflow | gcc -O3 | clang -O3 |
|---|---|---|---|
| 128 | 0 | rc=0, correct | rc=0, correct |
| 129 … 136 | +1 … +8 | **rc=0, silent, wrong answer** | **rc=0, silent, wrong answer** |
| 144 … 176 | +16 … +48 | rc=134 `*** stack smashing detected ***` | **rc=0, and it corrupts the CALLER's local** |
| 192 … 256 | +64 … +128 | rc=134 | rc=139 SIGSEGV |

The clang rows at +16…+48 print a garbage value for `main`'s own `T`: the
callee's overflow reached into the caller's frame and the program carried on.
That is the p02-style silent corruption, at the gate's own flags, with no flag
changed.

**So an `-fno-stack-protector` cell would be a thumb on the scale, and it is also
unnecessary.** Unnecessary, because the silent-corruption row already exists at
the shipped flags — in *both* compilers below +8, and in clang out to +48. A
thumb on the scale, because `-fstack-protector-strong` is what a Debian gcc
actually compiles with, so deleting it would make the C rung *less* like the C
that ships; and all it would buy is turning gcc's row into clang's, which the
matrix already has for free.

**What p12 does instead** is design one adversarial row per regime, so the ladder
itself is the result. On the shipped inputs (`-O3 isolated`, checksums against
`model.py`):

| input | overflow | c-gcc | c-clang | R1h and all four Rust rungs |
|---|---|---|---|---|
| `adversarial-exact` | 0 | rc=0, **agrees** | rc=0, **agrees** | rc=0, agrees |
| `adversarial-off1` | +1 | rc=0, **wrong answer** | rc=0, **wrong answer** | rc=0, agrees |
| `adversarial-nonul` | +6 | rc=0, **wrong answer** | rc=0, **wrong answer** | rc=0, agrees |
| `adversarial-overflow` | +128 | **rc=134** canary | **rc=139** SIGSEGV | rc=0, agrees |

**This is the first time in this project that `c-gcc` and `c-clang` differ in
observable BEHAVIOUR rather than in instruction count.** Everywhere else the two
C cells exist to separate "C is faster" from "clang's middle-end is faster"; here
they separate "the bug is caught" from "the bug is not", on identical source at
identical flags.

## 1. The second premise: `DST_CAP = 128` and the accept/reject mix

**The accept/reject mix is not a free parameter on `small`/`large`. It is pinned
to 100% accept by the gate**, and a `large` row with "a different acceptance
ratio" cannot be built.

`harness/check.py:1249-1278` (`check_checksums`) requires **every cell, R1
included, to print `model.py`'s checksum on every non-adversarial input**. R1
omits the capacity check and nothing else, so on any window where the check would
fire R1 copies bytes the checked rungs skip **and** ends with a larger `dlen` —
and both are folded into the answer. R1's checksum therefore differs
*necessarily*: for every value of `DST_CAP`, and for a truncating policy as much
as for a skipping one.

**This is structural for a WRITE bug and it has no analogue in the read
patterns.** p11 ships `adversarial-zerotail`: the same header lie as
`adversarial-count`, with a NUL tail, on which every rung *including R1* agrees
and nothing happens. A read that stays inside the allocation is a silent wrong
answer only when it reads different bytes; a write past a fixed local always
changes what the kernel folds back. **p12 cannot have a zerotail row.**

Two consequences, both stated rather than worked around:

- `small` and `large` exercise the capacity check on the **accept path only**, so
  they are **rank-deficient for §3's "per what?" question** — with everything
  accepted, *per string* and *per accepted string* are the same regressor.
- The acceptance axis therefore lives in `sweep-a*` and in the adversarial rows,
  and **R1 is absent from `sweep-a*`** for L ≥ 6, because it would copy `24·L`
  bytes into a 128-byte destination. That exclusion is the price of the bug being
  a write.

## 2. "The first WRITE precondition in this project" — it is the second

`patterns/p03-bounded-stack/verus.rs:273-314` already ships one:

```rust
// TRUSTED ITEM 3 of 5, and the project's first trusted item that WRITES through
// an unchecked index.
#[verifier::external_body]
fn stack_set_unchecked(v: &mut [u64; 64], i: usize, x: u64)
    requires i < old(v)@.len(),
    ensures  final(v)@ == old(v)@.update(i as int, x),
{ unsafe { *v.get_unchecked_mut(i) = x; } }
```

p12's `dst_set_unchecked` is that item with `u64` → `u8` and `64` → `128`, and
p12 inherits p03's `verus.unsafe_justifications` entry for the same
parameter-coverage false positive. **What is new is not the write, it is where
the bound comes from:**

| | p03 push | p12 copy |
|---|---|---|
| guard | `sp < STACK_CAP` | `dlen + slen <= DST_CAP` |
| where the guard is | **same basic block** as the store | **one loop level above** the store |
| what it bounds | a scalar that moves by 1 | a cursor that then advances by a whole string |
| what the prover needs | the guard | `dlen == dlen0 + (i − p)` ∧ `dlen0 + (q − p) ≤ DST_CAP` ∧ `i < q` |

That is p03's *pop* shape — the upper bound comes from the loop-carried
invariant rather than locally — sitting on a **write**. p03 measured that LLVM
gets the same-block case right and the loop-carried case wrong; §4 measures what
that costs here.

## 3. What the check costs, and what it is not

**Convention, stated once and used everywhere below: every `Ir` in this file is
the WHOLE-PROGRAM MARGINAL**, `(Ir at n_iters=200 − Ir at n_iters=100) / 100`,
`-O3 isolated`. `.memory/03-measurement.md` requires the marginal column for any
pattern whose kernel contains a bulk-memory call, and six of p12's seven cells
call one; `kernel_exclusive_ir` would silently drop the copy. Sweep numbers come
from `controls/sweep_ir.py`, matrix numbers from `results/gate/p12-strcat-fixed.json`.

### 3a. Static, and the finding is in the last column

`-O3 isolated`, `nm --print-size` extent:

| cell | `n_fn` | nopad | loops | library calls | panic pads |
|---|---:|---:|---:|---|---:|
| c-gcc (R1) | 139 | 137 | 4 | `memchr@plt`, `memcpy@plt`, `__stack_chk_fail@plt` | — |
| c-gcc-h (R1h) | 136 | 132 | 6 | `memchr@plt`, `memcpy@plt`, `__stack_chk_fail@plt` | — |
| c-clang (R1) | 146 | 143 | 3 | `memchr@plt`, `memcpy@plt` | — |
| c-clang-h (R1h) | 145 | 141 | 3 | `memchr@plt`, `memcpy@plt` | — |
| safe_naive (R2) | 231 | 224 | 6 | **none** | **7** |
| safe_tuned (R3) | 164 | 160 | 4 | `memcpy@GLIBC_2.14` | 2 |
| unsafe (R4) | 142 | 137 | 4 | `memcpy@GLIBC_2.14` | 0 |
| verus (R5) | 142 | 137 | 4 | `memcpy@GLIBC_2.14` | 0 |

The copy is a hand-written byte loop in the *source* of R1, R1h, R2, R4 and R5 --
`idiom.required[3]` requires it for the first three -- and **gcc, clang and rustc
all turn it back into a `memcpy` call, in every one of those cells except R2.**

⚠ **So the bounds check does not cost R2 a per-byte surcharge on top of a copy:
it costs R2 the copy IDIOM.** The mechanism is isolated by four cells that differ
in exactly one thing:

| copy spelling | destination write | `memcpy`? | loops | `n_fn` |
|---|---|---|---:|---:|
| byte loop, `dst[dlen] = b` (R2) | **checked, per byte** | **no** | 6 | 231 |
| byte loop, `dst[dlen] = b` in R3 (`s3_tuned_copy_byteloop`) | **checked, per byte** | **no** | 6 | 204 |
| `copy_from_slice` (R3 shipped) | checked, **per string** | **yes** | 4 | 164 |
| byte loop, `get_unchecked_mut` (R4) | unchecked | **yes** | 4 | 142 |

**A per-byte bounds check on the destination is what blocks the bulk lowering;
moving the same check to once-per-string brings it back, at zero `unsafe`.** That
is p09's lost-`load`-merge mechanism arriving on a *write*, and it is why the
safe-tuned rung is within 0.4% of the unsafe rung on wall clock (§3e) while the
safe-naive rung is 22% behind it.

Two consequences for how p12's numbers may be quoted, both from
`.memory/03-measurement.md`'s rule *"name the routine beside every rate and
difference rates only within a routine"*:

- **R3 − R4 is a within-routine difference** (both call `memcpy@GLIBC_2.14`) and
  it has an exact law -- §3c.
- **R2 − R4 is NOT**, and §3d shows it has no law at all outside a band where the
  string length is held fixed.

### 3b. What the capacity check costs in C, and the sign depends on the compiler

`R1h − R1` on the shipped matrix (`-O3 isolated`, whole-program marginal):

| | `small` (K=6) | `large` (K=31) |
|---|---:|---:|
| gcc | **−25.00** | **−125.00** |
| clang | **+7.00** | **+57.00** |

Swept over `sweep-n*` (K = 1..24, string length held at 4, 24 blobs) and the
five `sweep-a*` blobs R1 survives, **29 points, max |residual| 0.000000**:

| law | |
|---|---|
| `R1h − R1` **gcc** | **−4.00000·K − 1.00000** |
| `R1h − R1` **clang** | **+2.00000·K − 5.00000** |
| `R4 − (R4 with the check deleted)` **rustc** | **+2.00000·K − 6.00000** |

⚠ **The capacity check is not a cost in gcc. It is a saving of 4.00 instructions
per string**, and the two LLVM front-ends agree with each other and disagree with
gcc: `+2.00` per string in clang and `+2.00` per string in rustc, against
`−4.00` in gcc. This is p03's *"write it as 'any compiler asked to prove this',
never as 'safe Rust'"* arriving with the opposite polarity: the axis that decides
the sign is the **middle-end**, not the language. The third row is measured on
`.temp/p12/controls/d2_unsafe_nocheck`, which is R4 with the same one-line
deletion that turns R1h into R1, so all three rows are the same edit.

Both laws predict `large` -- K = 31, 3.5× outside the band's `K` range, on a
7.6 MiB blob where every call is a cache miss, against a band of 8-window
L1-resident blobs -- **exactly**: −4·31−1 = **−125.00** measured **−125.00**;
2·31−5 = **+57.00** measured **+57.00**.

### 3c. R3 − R4: an exact four-term law, and it goes NEGATIVE

Both rungs call `memcpy@GLIBC_2.14`, so this difference is within-routine and is
the one p12 can state as a law. Over **all 48 sweep blobs, max |residual|
0.000000**:

```
R3 − R4  =  +5.00000                      per call
            −4.00000 · K                  per string WALKED
            +3.00000 · nacc               per string ACCEPTED
            +4.00000 · [dlen mod 4 ≠ 0]   the destination fold's 4x unroll epilogue
```

equivalently **−1.00 per accepted string and −4.00 per REJECTED string**. The
`mod 4` term is the epilogue of the byte-at-a-time Horner fold, which LLVM
unrolls 4× (the same constant p11's `inputs/gen.py` records); it is 0 on 36 of
the 48 blobs and exactly +4.00 on the other 12, and those 12 are precisely the
blobs whose `dlen` is not a multiple of 4.

**Out of sample it predicts both measured inputs exactly**, with zero further
parameters:

| | K | nacc | dlen | predicted | measured |
|---|---:|---:|---:|---:|---:|
| `small` | 6 | 6 | 123 | **+3** | **+3.00** |
| `large` | 31 | 31 | 124 | **−26** | **−26.00** |

`small` and `large` sit outside the band on every axis the band moves -- mean
string length 20.5 and 4.0 against a band held at 4 or at K = 24, 100 and 50 000
windows against 8, L1-resident against 7.6 MiB.

⚠ **So the shipped safe-tuned rung is 26.00 Ir per call CHEAPER than the shipped
unsafe rung on `large`, and 3.00 dearer on `small`** -- the sign of p12's
"safety tax" is decided by the string count, and it crosses zero at
`K = 8` when every string is accepted. This is the fourth measured instance of
`.memory/01-ladder.md`'s R4-by-permission result and the first where the safe
rung beats the unsafe one on a *shipped* pair with no respelling on either side.

### 3d. R2 − R4 has no per-byte law, and that IS the result

On `sweep-n*`, where the string length is held at 4, it is exact:

```
R2 − R4  =  +53.00000 · K  +  12.00000       (24 blobs, max |residual| 0.000000)
R2 − R3  =  +54.00000 · K  +   7.00000       (24 blobs, max |residual| 0.000000)
```

On `sweep-a*`, where the string length walks 1..24, **the same expression is out
by up to 1296 Ir/call**, and no linear model in `(1, K, nacc, xscan, xdst)` does
better than a max residual of 548 (23% of the quantity). The reason is not noise:
R4's copy is a `memcpy` call whose cost is a **step function** of the individual
string length, and R2's is a scalar loop that is linear in it. Even inside the
all-accept region the per-copied-byte figure wanders -- 13.500, 12.250, 12.500,
13.375, 13.300 at L = 1..5 -- which is the size dispatch and not a rate.

**So p12 does not publish a per-byte safety tax for R2, and a five-decimal one
would be a fiction.** What it publishes is the mechanism in §3a and the fixed-`L`
law above.

## 4. Two range checks, one bound, two answers -- and what the optimiser did

R3 is one function containing p03's question twice over:

- `dst[dlen..dlen + slen].copy_from_slice(&w[p..q])` -- the fact the range check
  needs, `dlen + slen <= DST_CAP`, is tested **one line above, in the same basic
  block**;
- `dst[..dlen].iter()` -- the fact the range check needs, `dlen <= DST_CAP`,
  comes from the **loop-carried invariant** of a loop that has already exited.

**Measured: two panic landing pads survive in R3** (§3a), against seven in R2 and
zero in R4. Respelling the destination fold three ways -- shipped iterator,
`s1_tuned_indexed_fold`, `s2_tuned_bytefold_reslice` -- leaves the count at **2
in all three** and moves the marginal by at most 1.00 Ir/call, so the fold's
check is not deleted by any admissible spelling of the fold. p03's result
transplants: the guard that is local is elided, the bound that is loop-carried is
not.

⚠ **What was NOT done**: identifying *which* two of R3's checks the two surviving
pads belong to. The count is off the listing and is a fact; the attribution would
need the panic `Location` symbols and was not attempted.

## 5. Keeping the `requires` at ONE clause — three routes, all three priced

The kernel's `requires` is the single structural clause `off + len <=
buf@.len()`. Two program lines are what keep it there, and neither is free.

**5a. `if q >= len { break; }`** — p11's line, for p11's reason, carried by every
p12 rung. p11 measured it at 1.00000 Ir per scanned byte and 8.5% of its R4. It
is in `idiom.required` here for all seven rungs, so no p12 rung comparison moves
on it, and p12 does not re-measure it.

**5b. `slen <= DST_CAP` as the left conjunct of the capacity test.** Without it,
`dlen + slen` is `usize` addition on a `slen` that nothing at the pinned vstd
bounds below `usize::MAX`, and Verus refuses it. Measured, on twins generated
from the shipped `verus.rs` by exact-string substitution:

```
$ python3 patterns/p12-strcat-fixed/controls/gen_controls.py
$ ./verus_run.py .temp/p12/controls/r1_verus_plain_additive.rs
error: possible arithmetic underflow/overflow
   --> .temp/p12/controls/r1_verus_plain_additive.rs:478:12
    |
478 |         if dlen + slen <= DST_CAP {
    |            ^^^^^^^^^^^
verification results:: 14 verified, 1 errors

$ ./verus_run.py .temp/p12/controls/r2_verus_subtraction_first.rs
verification results:: 15 verified, 0 errors

$ ./verus_run.py patterns/p12-strcat-fixed/verus.rs           # shipped
verification results:: 15 verified, 0 errors
```

Three routes to the same obligation, and the ordering is not the one anyone would
guess. Static `n_fn` of the R4-side exec code, `-O3 isolated`, all three printing
the identical checksum on `small`:

| route | spelling | `requires` clauses | driver conjuncts | `n_fn` | Δ |
|---|---|---:|---:|---:|---:|
| A (p17's) | `dlen + slen <= DST_CAP` + `buf@.len() <= isize::MAX` | 2 | 3 | 140 | **0** |
| **C (shipped)** | `slen <= DST_CAP && dlen + slen <= DST_CAP` | **1** | **2** | 142 | **+2** |
| B (p02's idiom) | `slen <= DST_CAP - dlen` | 1 | 2 | 144 | +4 |

Every `n_fn` above is measured on the R4-side exec code built by
`controls/gen_controls.py` — `r3_unsafe_plain_additive` 140,
`r4_unsafe_subtraction_first` 144, shipped `unsafe.rs` 142 — and all three print
`12909139622517405579` on `small`. Route A's precondition and driver conjunct are
ghost and cost no instructions; that is p17's measured result and it is why the
row reads 0.

⚠ **The subtraction-first respelling this project adopted as its safe idiom on
p02 and p16 is the DEAREST of the three here.** `DST_CAP - dlen` is a constant
minus a loop-carried variable, so it cannot be folded into the compare the way
`dlen + slen <= 128` can.

WARNING -- **routes A and B are OUT OF CONTRACT as p12 declares it**, and that is
not an accident: `idiom.required[1]`'s Rust spelling pins
`if slen <= DST_CAP && dlen + slen <= DST_CAP {` literally, so a rung that
respells the test fails the declaration. Checked with the gate's own matcher and
not by eye (section 11c): `r3_unsafe_plain_additive` and
`r4_unsafe_subtraction_first` both miss `required[1]`, where the shipped
`unsafe.rs` misses none of the entries it scopes to. **So the table above prices
the PIN, and it is not an in-contract R4-side span.** The in-contract R4 side of
p12 has zero measured width -- section 11a.

**Route C ships**, and the +2 instructions per string is the price. Three reasons
it is preferred over A: the `requires` stays at one clause and the driver at two
conjuncts, which keeps p12's contract directly comparable with p03's and p11's;
the additive spelling the pattern is about survives verbatim on the right of the
`&&`; and A's zero is already a published p17 result, where C's number is new.

⚠ **And C's +2 is charged to the four Rust rungs only.** R1h keeps the plain
`if (dlen + slen <= DST_CAP)`, because R1h is not chained to the prover and
putting the conjunct there would charge the C column for a Verus concession. So
this is, as far as this project's records go, **the first measured price the
`identity` pin has extracted from a SHIPPED cell** rather than from a variant it
disqualified: `.memory/01-ladder.md`'s R4-by-permission instances (p16's `u_c32`,
p11's `r4_cstr`, p05's `r4_dataslice`) are all "this variant cannot be a rung".
Here the rung pays, uniformly, +2 per string, and every Rust-side rung comparison
is unaffected because all four carry it.

## 6. The proof, the TCB and the obligation count

**Verus: `15 verified, 0 errors`, on the second attempt.** The first attempt was
`14 verified, 1 errors` — `invariant not satisfied before loop` on the
destination fold's `dlen <= DST_CAP`, because `invariant_except_break` facts do
not survive the outer loop's `break` and the loop's `ensures` did not yet carry
them. Adding `dlen <= DST_CAP` and `dst@.len() == DST_CAP` to the outer loop's
`ensures` fixed it. **No lemma, no `by (nonlinear_arith)` anywhere in the
kernel** — every multiplication in it is by a literal, exactly as on p11 and p03.

Obligation decomposition, each term measured with

### SLB-TRUSTED-ARGUMENT verus.rs buf_get_unchecked

(a) *Is the twin's body the right checked stand-in?* The trusted body is
`unsafe { *v.get_unchecked(i) }` and the twin's is `v[i]`. The two are the same
operation with and without the bounds check, and Verus specifies the checked one
with exactly the obligation `i < v@.len()`, so a `requires` too weak to license
the unchecked read is too weak to license the checked one — which is what the
gate's per-conjunct deletion probe checks on every run rather than taking on
trust. This accessor is character-for-character the one p01, p02, p03, p05, p07,
p11, p16 and p17 ship; it is not new here and no p12-specific argument is needed
for it beyond (b).

(b) *Is the `ensures` complete with respect to every unchecked operation the body
performs?* The body performs exactly one unchecked operation, a read of `v` at
`i`, and the `ensures` `r == v@[i as int]` determines the result of that read
completely. It is **not** complete in the stronger sense `.memory/04-verus.md`
names: a body that additionally read `v[i + 1]` and discarded the value would
satisfy this contract, this twin and every gate stage, because an extra
*unlicensed read* leaves no trace in a return value. That blind spot is not
closed by anything in the gate and the only backstop is Miri on `unsafe.rs`,
which is why `miri.required` is true. What the clause does buy is that the read
is *at `i`* and *of `v`*, so the functional `ensures` on `kernel` is a statement
about the window's bytes and not about arbitrary memory.

(c) *Does each clause mean the same in both configurations?* Yes. The `requires`
and `ensures` are lifted from the trusted item by the gate and compared against
the twin's character for character, they mention no constant and no `cfg`-gated
name, and `v@.len()` is the same spec function in both builds. The token
`slb_twin` appears only inside the three twins' own `#[cfg(slb_twin)]`
attributes, which the gate's token scan checks.

### SLB-TRUSTED-ARGUMENT verus.rs dst_get_unchecked

(a) *Is the twin's body the right checked stand-in?* The trusted body is
`unsafe { *v.get_unchecked(i) }` on a `&[u8; 128]` and the twin's is `v[i]`.
Verus specifies the checked indexed read on a **fixed-size array** with the same
`0 <= i < N` obligation, so the substitution is the same one as for the slice
accessor above, on an array type. p03's `stack_get_unchecked` is the same item on
`[u64; 64]`, and p12 is the second pattern to need an array accessor rather than
a slice one.

(b) *Is the `ensures` complete with respect to every unchecked operation the body
performs?* The body performs exactly one unchecked read and `r == v@[i as int]`
determines it. The `requires` is deliberately ONE conjunct: a second clause
`v@.len() == 128` would be a **tautology** for a `&[u8; 128]`, discharged from
the parameter type alone by vstd's `array_len_matches_n`, and p03's gate run
refused exactly that draft — stage 5c-req's tautology probe reported it and stage
5c-twin's per-conjunct deletion showed the twin never used it. A tautological
conjunct on a *trusted* item is the shape `.memory/04-verus.md` warns about, so
it is not written here. The extra-unlicensed-read blind spot of (b) above applies
unchanged; Miri is the backstop.

(c) *Does each clause mean the same in both configurations?* Yes, on the same
grounds as `buf_get_unchecked`: one conjunct, no constant, no `cfg`-gated name,
and `v@.len()` on a `[u8; 128]` is the array view's length in both builds.

### SLB-TRUSTED-ARGUMENT verus.rs dst_set_unchecked

(a) *Is the twin's body the right checked stand-in?* The trusted body is
`unsafe { *v.get_unchecked_mut(i) = x; }` and the twin's is `v[i] = x;`. Verus
specifies the checked indexed **store** on an array with the same `0 <= i < N`
obligation, so a `requires` too weak to license the unchecked store is too weak
to license the checked one, and the gate's deletion probe confirms on every run
that the twin *uses* the precondition rather than merely carrying it. This is the
**second** trusted item in this project that writes through an unchecked index
(p03's `stack_set_unchecked` is the first, and this one is that item at
`u8`/`128`), and the first whose licensing guard is a **loop level above** the
store rather than in the same basic block — see §2.

(b) *Is the `ensures` complete with respect to every unchecked operation the body
performs?* The `requires` is one conjunct, `i < old(v)@.len()`, which for a
`&mut [u8; 128]` reads `i < 128`; the tautological second conjunct is omitted for
the reason given under `dst_get_unchecked`. The body performs exactly one
unchecked operation — a store of `x` into slot `i` — and the single `ensures`
clause states it as a **whole-sequence equality**,
`final(v)@ == old(v)@.update(i as int, x)`, rather than as a property of slot `i`
alone. That is the shape `.memory/02-bench-rules.md` argues for in its p02 worked
example: one clause says both *"slot `i` became `x`"* and *"nothing else moved"*,
so a body that also wrote slot `i + 1` would **contradict** the `ensures` instead
of slipping past it. This is where a write is better off than a read: for a read,
an extra unlicensed access is invisible to any `ensures`; for a write into a
value the `ensures` fully determines, it is not. It is **not** closed — a write
*outside* `v` altogether would still be invisible, exactly as p08's
`copy_nonoverlapping` substitution was — so Miri on `unsafe.rs` remains the
backstop and is why `miri.required` is true. On p12 that matters more than on any
earlier pattern, because this item is the one the entire memory-safety claim
rests on: R1's bug is precisely a store at an `i` this `requires` forbids.

(c) *Does each clause mean the same in both configurations?* Yes. The `requires`
is the single conjunct `i < old(v)@.len()` and mentions no constant at all;
`old(v)` and `final(v)` are Verus's own `&mut` spellings and are not
configuration-dependent; `Seq::update` is the same spec function in both builds;
and the gate's token scan reports `slb_twin` only on the three twins' own
attributes. The one asymmetry worth naming is that this item's `requires` does
**not** constrain `x`, and that is declared in `spec.md`'s
`verus.unsafe_justifications` and shouted by the gate on every run rather than
being left for a reader to notice: `x` is a pure value parameter, stored and
never used as an address, an index or a length, so every `u8` is a legal thing to
put in a `u8` slot and there is no precondition a caller could usefully supply.

## 7. What safe Rust cannot express, and the two controls that show it

`controls/gen_controls.py` builds R2 and R4 with **the capacity check deleted** --
the same one-line edit that turns `c/kernel_hardened.c` into `c/kernel.c`.

| input | overflow | R1 (gcc / clang) | `d1` R2, check deleted | `d2` R4, check deleted |
|---|---|---|---|---|
| `adversarial-exact` | 0 | agrees / agrees | **agrees** | agrees |
| `adversarial-off1` | +1 | wrong answer / wrong answer | **panic, exit 101** | wrong answer, exit 0 |
| `adversarial-nonul` | +6 | wrong answer / wrong answer | **panic, exit 101** | — |
| `adversarial-overflow` | +128 | abort 134 / SIGSEGV 139 | **panic, exit 101** | SIGSEGV 139 |

```
thread 'main' panicked at d1_naive_nocheck.rs:71:17: index out of bounds
```

Three things are worth reading off it:

1. **Safe Rust cannot express the bug.** The deletion that produces R1 produces,
   in safe Rust, a rung that stops. There is no safe spelling of `dst[dlen] = b`
   that writes past a `[u8; 128]`, so the capacity check in R2/R3/R4 is a
   *semantic* line -- it decides which strings are copied -- and never a safety
   one. p08 established this shape for aliasing; p12 is the same shape on length.
2. **The +1-byte row is the sharp one.** At `adversarial-off1` both C compilers
   run to completion and print a wrong answer with no diagnostic of any kind, and
   safe Rust panics. Nothing about the magnitude is special to Rust: the same one
   byte is what UBSan reports and what neither canary sees.
3. **Unsafe Rust IS C.** `d2` prints `11317652573463608704` on
   `adversarial-off1`, which is **byte-for-byte the answer `c-gcc` and `c-clang`
   print**, and segfaults on `adversarial-overflow` exactly as clang does. The
   `unsafe` rung has no safety margin over C to lose; what R5 adds is the proof
   that the deletion cannot happen unnoticed (§9, mutant `p1`).

`d2` is a **control and never a rung** -- it is unsound by inspection, which
`.memory/01-ladder.md` forbids of an R4. Miri sees it, on the +1-byte input:

```
$ miri --sysroot ... --edition 2021 -Zmiri-disable-isolation \
      .temp/p12/controls/d2_unsafe_nocheck.rs -- <adversarial-off1, n_iters=4>
thread 'main' panicked at d2_unsafe_nocheck.rs:85:31:
unsafe precondition(s) violated: slice::get_unchecked_mut requires that the
index is within the slice
error: abnormal termination: the program aborted execution

$ miri ... patterns/p12-strcat-fixed/unsafe.rs -- <the same blob>
5907921001705515200                       <- shipped R4: clean, and correct
```

### 7a. Who sees the ONE-BYTE overflow

`adversarial-off1` is `adversarial-exact` plus one 1-byte string, so exactly one
byte lands outside `dst`. Every mechanism in the project's toolbox, on that one
input:

| mechanism | verdict on +1 byte |
|---|---|
| gcc `-fstack-protector-strong` canary (`c-gcc`) | **silent**, exit 0, wrong answer |
| clang, no canary (`c-clang`) | **silent**, exit 0, wrong answer |
| gcc ASan + UBSan at the gate's flags | **fires**: `index 128 out of bounds for type 'uint8_t [128]'` |
| safe Rust's own bounds check (`d1`) | **panics**, exit 101 |
| Miri on unsafe Rust (`d2`) | **fires**: `get_unchecked_mut requires that the index is within the slice` |
| the Verus proof (mutant `p1`, section 9a) | **fails**, on the write bound |

⚠ **The two things that ship in production are the two that say nothing.** That
is the p12 sentence, and it is one byte -- not the 128-byte smash that gets
drawn in the diagrams.

## 8. The narrow-type control: a check that is present, looks right, and waves it through

`spec.md` pins the capacity test in `size_t`/`usize`. `controls/gen_controls.py`
builds `n1_uchar_sum`, which is `c/kernel_hardened.c` with the sum computed in
`unsigned char`:

```c
unsigned char sum = (unsigned char)(dlen + slen);
if (sum <= DST_CAP) { ... }
```

It is not a strawman: `dlen` never exceeds 128 in the checked kernel and a
128-byte destination positively invites a byte-wide length. `narrow.bin` (built
by the same script: one window, a 256-byte string followed by an 8-byte one)
separates it from the shipped cell:

| cell | check | result on `narrow.bin` |
|---|---|---|
| `c-gcc-h` (R1h) | `size_t` | `8190881893342254720` -- correct, rejects the 256-byte string |
| `safe_naive` (R2) | `usize` | `8190881893342254720` -- correct |
| **`n1_uchar_sum`** | `unsigned char` | ***** stack smashing detected *****, exit 134 |
| `c-gcc` (R1) | **none** | ***** stack smashing detected *****, exit 134 |

`(unsigned char)(0 + 256) == 0 <= 128`, so the check passes and 256 bytes are
copied into a 128-byte array. **A hardened cell whose check is written one type
too narrow is indistinguishable from the cell with no check at all**, on an
input a 40-byte window can express. That is what makes R1h worth shipping
(`.memory/01-ladder.md`, "R1 vs R1h = what the check costs, inside one
language") and it is the p12 answer to "the hardened cell is the safe one, so
what is left to get wrong?"

⚠ Note it needs a **256**-byte string and not a 129-byte one: the wrap has to
carry the sum below `DST_CAP`, not merely past it. In `uint16_t` the same defect
needs a 65 536-byte string, which p12's windows can also express but only in a
64 KiB window; in `int` it is unreachable for any input this wire format can
build. So the narrow-type family is real but its reachability is a function of
the width, exactly as p07 measured for its midpoint overflow.

### 9a. `p1_no_capacity_check` -- R1's bug, written into R5

## 10. The sweep, and the rank of the pooled design

`controls/sweep_ir.py`, 48 blobs, `-O3 isolated`, whole-program marginal.

- **band N** (`sweep-n{K}L04`, K = 1..24): the string-count axis, string length
  held at 4, **every string accepted**.
- **band A** (`sweep-a24L{L}`, L = 1..24): the acceptance-ratio axis, count held
  at 24, so `nacc = min(24, 128/L)` falls from 24 to 5 while scanned bytes rise
  linearly and copied bytes saturate near 128.

⚠ **The rank, reported because a band holding one regressor constant cannot
identify it** (`.memory/01-ladder.md`, p03 and p09). Regressors
`(1, K, nacc, xscan, xdst)`:

| design | n | rank |
|---|---:|---:|
| band N alone | 24 | **2 / 5** |
| band A alone | 24 | **4 / 5** |
| **pooled** | 48 | **5 / 5** |

Band N is rank 2 because with nothing rejected `nacc = K`, `xscan = 5K` and
`xdst = 4K` are all proportional to `K` -- which is **exactly the deficiency
`small` and `large` have** (§1), and the reason band A exists. `sweep_ir.py`
prints `SINGULAR` rather than a fit whenever a series' usable subset is
rank-deficient, so a per-band fit cannot return garbage at zero residual: the two
R1 series do exactly that, because R1 survives only 29 of the 48 blobs.

⚠ **One collinearity no input can break.** The copy loop runs `dlen` times and
the destination fold runs `dlen` times, **by construction** -- every accepted
byte is copied once and folded once. So `xcopy` and `xfold` are the same
regressor and p12 cannot separate the cost of writing a byte from the cost of
reading it back. They are reported as one term, `xdst`, and a decomposition would
need a control that deletes one of the two loops (p11's one-loop-at-a-time
control) rather than another input.

⚠ **R1 is not measurable on band A for L ≥ 6**, because it would copy `24·L`
bytes into a 128-byte destination: gcc aborts on the canary from L = 6 and clang
segfaults from L = 8. That is the price of the bug being a write, and it is why
the two R1 laws in §3b are fitted on 29 points and the rest on 48.

### 10a. The two blobs where the benchmark harness itself was a casualty

At `sweep-a24L06` and `sweep-a24L07`, clang's R1 exits 0 and the two-point
marginal came out **exactly 0.0**. It is not noise:

```
n_iters=    1 c-clang  rc=0 out=10464138362225408507
n_iters=    2 c-clang  rc=0 out=10464138362225408507
n_iters=    4 c-clang  rc=0 out=10464138362225408507
n_iters=  100 c-clang  rc=0 out=10464138362225408507
n_iters=  200 c-clang  rc=0 out=10464138362225408507
n_iters= 1000 c-clang  rc=0 out=10464138362225408507
```

(against `c-clang-h` and `safe_naive`, which give six different answers for the
six values, as they must.) **The kernel's overflow reached into `main`'s frame
and destroyed the driver's own loop state**, so `while (it < inp.n_iters)` stopped
depending on `n_iters` at all. This is the +16…+48 regime of §0 seen from the
other end: the corruption is not confined to the kernel that caused it, and any
measurement of an overflowing R1 is measuring an unknown number of calls.

`sweep_ir.py::usable()` therefore refuses a marginal of 0 as a datum, and says
so. Two blobs is a small number, but the failure mode is silent, so the check
stays.

### 11c. Every control checked against the gate's own matcher

`.memory/01-ladder.md`'s standard is decided by `check.py::spelling_matches`, not
by reading, and p03 shipped two controls the ruler rejects. So every control in
this file was run through it before being quoted. A control is in contract when
it misses no more `required` entry than the rung it varies and hits no
