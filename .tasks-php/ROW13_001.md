## 3. ⭐⭐⭐ `ph66`'s STATED BLOCKER IS DISSOLVED, AND IT NAMED THE WRONG DIRECTION

`CATALOGUE.md`'s `ph66` block: *"The DJBX33A preimage the fixture needs was
never computed; compute it before building."*

⛔ **The preimage direction is infeasible and it is also not what the fixture
needs.** Verified against the pinned tarball (sha `5783e0c0…d6919`):

1. `Zend/zend_hash.h` — `static inline ulong zend_inline_hash_func(char *arKey,
   uint nKeyLength)`, `hash = 5381`, `hash = ((hash << 5) + hash) + *arKey++`.
   **DJBX33A, accumulating in a `ulong`.**
2. `Zend/zend_types.h` — `typedef unsigned long zend_ulong;` → **64-bit on
   LP64.** ▶ A preimage is a **64-bit** target. Every `33^k` is odd, hence a
   **unit** mod 2^64, so no byte position owns a bit range and digit-lifting
   cannot work; 2^64 is not searchable. It would need CVP or ~2^32
   meet-in-the-middle. ⓘ **I tried the lifting approach and it failed for
   exactly this reason — recorded because the failure is the evidence.**
3. ⭐⭐ **NO PREIMAGE IS NEEDED.** In `_zend_hash_index_update_or_next_insert` a
   numeric bucket stores `p->h = h` with `h` **the raw user-chosen index**, and
   its lookup predicate is `(p->nKeyLength == 0) && (p->h == h)`.
   ▶ **Run the hash FORWARDS on any string key and use the result as the integer
   index.** `"abc"` → **`6385036779`**. One line, no search.
4. `nKeyLength` **includes the NUL** — `Zend/zend_execute.c:3612` passes
   `varname->value.str.len + 1`.

Then `Zend/zend_hash.c:461-462` (`zend_hash_del_key_or_index`):

```c
if ((p->h == h) && ((p->nKeyLength == 0) || /* Numeric index */
    ((p->nKeyLength == nKeyLength) && (!memcmp(p->arKey, arKey, nKeyLength))))) {
```

**The left disjunct fires on the numeric bucket and the key is never compared.**
