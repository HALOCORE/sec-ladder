\section{Introduction}
\label{sec:intro}

Most serious security bugs in C and C++ code are memory-safety bugs: reads and writes that land outside the object they were meant for \cite{msrc19}\cite{chromium}. Three remedies are on offer — write the missing checks into the C, rewrite in a memory-safe language such as Rust, or keep the unsafe code and prove it correct with a verifier — and each arrives with two numbers, what it costs and what it guarantees, both usually quoted without the conditions that produced them. A benchmark reports that safe Rust is 30% slower than C without saying which Rust program was compared with which C program, who tuned each, or which input was run; a guarantee is quoted — "memory safe", "verified" — without saying which bugs it reaches. The two programs behind a cost figure are almost never the same program, so the number mixes the price of safety with the price of a different author.

This paper holds the program fixed and varies only the safety mechanism. We took \num{totals.passing.patterns} small C programs, each built around one real bug from a named class — a missing bounds test, a use after free, a type confusion, an overlapping copy — and wrote each one six ways (Section \ref{sec:method}). Two are C: the plain program with its bug, and the same program with the missing check written in. Two are safe Rust: a line-for-line port, and a version tuned by hand. Two are unsafe Rust: one with the bounds checks switched off, and that same code carrying a machine-checked Verus proof \cite{verus23} that every unchecked access is in bounds. Every version was compiled at two optimisation levels, run under a deterministic instruction counter, checked against a Python reference implementation, and attacked with inputs written to trigger that program's bug.

Three questions organise the results. **What does memory safety cost**, and what is the measured cost actually paying for (Section \ref{sec:cost})? **What does each version do under attack**, and which bugs does memory safety not reach (Section \ref{sec:reach})? **What does a proof cost, and what does it prove** (Section \ref{sec:proof})?

The paper makes three contributions. The first is the method: one program, six versions that must agree on every well-formed input, a proof forbidden from changing the machine code, and a rule that a difference is only reported where the two versions call the same things outside the measured function. The second is eleven findings, each stated once in a numbered box with its evidence beneath it; the boxes alone are a complete short version of this paper. The third is an account of where the method's own errors run and of the bugs the guarantee does not reach. Section \ref{sec:lessons} turns the findings into rules for anyone publishing or reading a safety number, Section \ref{sec:threats} says what the study cannot tell you, and Section \ref{sec:related} places it.
