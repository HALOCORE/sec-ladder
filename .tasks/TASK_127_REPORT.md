## §B — the design: **recompute-and-compare (§B3), and the manager's lean was right about the shape and wrong about the risk**

§B3 wins on the measurement above: it needs no projection to drift, no path list
to rot, it covers all three inputs at once, and it is the only spelling that also
notices a `report.py` change that alters the output. §B2 (a projection hash)
would additionally have needed a *new pin line written into every table*, i.e.
the same 26 re-renders, plus the two-implementations hazard §B names.

**But the risk the manager named is not the risk this design has.** The worry was
*"the gate then fails for a REPORTING reason if `report.py` reads something
volatile"*. It does not — §A settles that. The real defect is different, and I
would have shipped it if I had only run the arms the task listed:

### ⚠⚠ 1. THE NAIVE §B3 IS SELF-REFERENTIAL AND OSCILLATES WITH PERIOD 2

`report.py::shout_section` printed the gate record's **`verdict`** into the
table. `verdict` is an **output of the gate run stage 9c runs in**. So:

```
run N    9c fires -> rep.fail -> this run's verdict is FAIL -> the record says FAIL
report.py         -> the table now prints  verdict `FAIL`
run N+1  render(FAIL record) == table -> FRESH -> verdict PASS -> record says PASS
run N+2  render(PASS record) != table -> FIRES AGAIN -> ... forever
```

**It never settles, and it starts the first time the check does its job** — so
the MUST-NOT-FIRE arm on an unchanged tree, which the task file (rightly) called
the arm that decides the design, **would have passed and missed it.**

Measured before fixing (`probe_selfref.py`): **19 of 26 tables changed bytes when
the record's `verdict` changed** — every pattern that renders a shout section.

⚠ **`rep.shout` would be worse, not better**: `loud` is rendered by
`shout_section`, so a shout is the same defect wearing a milder verb. Stage 9c
uses `rep.fail` only; `failures` is measured not-read.

**Fix, and it is at the source rather than in the checker: `report.py` no longer
renders `verdict`.** After it, `--selfref` reports **0 of 26 × 9 run-scoped keys
reaching the render**, and the render is a deterministic function of committed
sources. The section now says *why* the verdict is absent and where to read it.
Cost: 19 tables, one line each. The regression detector is
`harness/tools/table_render_inputs.py --selfref`, exit 1 if it ever comes back.

### 2. The one-run lag: **status quo, not a new defect**

Stage 9c runs before the record is written, so it reads the *previous* run's gate
record. **Stage 9 has exactly the same shape** — `report.py` prints the
*record's* `contract_sha256`, not `spec.md`'s — which is why TASK_121 documented
the loop as *gate → `report.py` → gate, twice*. I considered moving 9c after the
write to remove the lag and **rejected it**: the failure would then have to
mutate a record already on disk, which reintroduces the self-reference. Named in
the docstring so the next person does not "fix" it.

### 3. A `verdict` flip could have bitten even without the self-reference

Before removing it I costed the other route into the render. `MIRI_TIMEOUT` is
180 s and `.memory/00-environment.md` measures a **two-state 4.6× Miri
slowdown**, so any row above 180/4.6 = 39.1 s can gain or lose a blocked row and
flip `PASS ↔ PASS-WITH-BLOCKED-ROWS`. **Exactly three rows are above it, all on
p01/p42, both already `PASS-WITH-BLOCKED-ROWS`; the other 24 patterns' slowest
Miri row is ≤ 4.3 s — a 42× margin.** `blocked` itself is not rendered, so 1-vs-3
blocked rows is invisible. Moot now, recorded because it was not.

## ⚠⚠ The manager's three least-sure calls, answered with the measurement

**1. Is recompute-and-compare (§B3) the right shape?** ✅ **Yes, and your reason
for doubting it was the wrong reason.** §B1 is dead by measurement (21/26 fire on
their own gate run). §B3's render is stable 26/26 across two real draws. The
gate-depends-on-the-reporter worry does not bite — `report.py` reads nothing
volatile — but **the design had a self-reference through `verdict` that no

**2. Is it worth a 57.5-minute sweep, versus a one-line rule that always
re-renders all 26 tables?** ⚠⚠ **The cheap alternative is not cheaper, and the
reason is historical rather than technical: IT WAS ALREADY PROPOSED AND NOT
ADOPTED.** `TASK_096_REPORT.md` item 7b said, in these words, *"**Add
`harness/report.py pNN` to the sweep recipe**, or a staleness check."* The
project took the staleness check; the recipe half was never wired, and **nothing
in the tree runs `report.py` today** (`grep -rn 'report\.py'` over `*.py`/`*.sh`
finds no caller). After that recommendation the class recurred **twice** — p09
16 tasks stale, p23 with no table at all. So:

* a recipe is **prevention that holds only while a human runs it**, and the
  assumption that a human runs it is precisely the one that failed, twice, in a
  world where the recipe already existed;
* a recipe leaves **no artefact**. The gate stage writes `table_render` into all
  26 records, so "was this table current?" becomes checkable after the fact;
