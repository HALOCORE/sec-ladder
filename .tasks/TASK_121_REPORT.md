## §A — the design call

### The digest: option (a), and the argument for it is NOT the one in the task file

**`derived_from_sha256` = `measure.py::measurement_sources(PDIR)` ∪ {the 15 sweep
blobs the run actually opened} ∪ {`controls/sweep_fit.py` itself} = 34 paths.**

* `measurement_sources` is **reused, not re-listed**. It is the project's single
  answer to "committed files whose contents can change a number", the six
  `-O3 isolated` binaries are built from exactly that set, and a second
  hand-rolled copy is a list that rots. It is mildly over-broad (`asm.py`,
  `measure.py`, `model.py`, `common/slb.py` cannot move a number here); over-broad
  is the safe direction and costs 47 s to clear.
* **The blobs, per the task file's missed term.** `SKIP_INPUT_PREFIX = "sweep-"`
  is correct for `measure.py` and wrong for a sidecar whose every row is one of
  those blobs. Option (b) is rejected on `measure.py::matrix_inputs`'s own
  grounds — *"the generator hash cannot tell 'the inputs changed' from 'a comment
  changed'"* — which applies here unchanged, so `gen.py` **and** the blobs are
  hashed. Only the **15 read**, not the 107 present: adding a band must not stale
  a fit that never looked at it.
* **The script itself**, because `want_m`, `want_k`, `CELLS` and `kernel_ir`'s
  regex decide what the rows are. Not self-referential — the sidecar is not
  hashed, only its generator.

⚠⚠ **THE COST PREMISE THE WHOLE DESIGN IS USUALLY ARGUED FROM IS FALSE, AND I
MEASURED IT.** `.memory/05-layout.md` and `TASK_121` §A.1 both say pinning
against the gate digest would cost *"~30 minutes of callgrind"* to clear on a
prose fix. **A full `sweep_fit.py` regeneration is 47 s**, timed twice, and the
output was **byte-identical to HEAD**. So the case for pinning narrowly is the
**signal**, not the price: a `STALE` that fires when nothing determining the
numbers has moved trains readers to clear it reflexively and makes the gate
verdict a function of prose. That reason survives; the cost reason does not.

✅ **Free by-product: `sweep_fit.json` was not stale.** Nothing in the tree could
have said so before today, which is the item.

### The key: a new one, `derived_from_sha256`, and `gate_source_sha256` kept

Stage `9b`'s old key would have become a lie. Rather than rename it, the stage now
takes **either**:

* **`derived_from_sha256`** — a `{repo-relative path: sha256}` dict the sidecar
  writes *for itself*. The stage just re-hashes the named paths, so it needs **no
  knowledge of any generator** and generalises to any future sidecar in any
  pattern. Preferred, and what `sweep_fit.json` uses.
* **`gate_source_sha256`** — unchanged semantics, kept for a sidecar that
  genuinely derives from the whole gate record (`synthesis/licence.json`'s shape).
  The name is no longer a lie because it now means exactly what it says.

Verdicts: **moved hash → FAIL**; **path absent → SHOUT** (`MISSING-SOURCES`,
mirroring `measure.py::check_stale`'s MISSING/STALE split — the blobs are
gitignored and a fresh clone must not go red for it); **neither key → SHOUT**
(unchanged). The `pin.regenerate` / `pin.restore_missing` strings are printed in
the failure message, because a stale verdict nobody knows how to clear is how
gates get switched off.

### ⚠⚠ The pin would have OVERCLAIMED, and I found it by applying `.memory/03-measurement.md`'s entry-8 question

*"Would its FAILING mean what its PASSING means?"* — **no, at first.**
`sweep_fit.py` reads pre-built binaries from gitignored `.temp/build/p23/` and
never checked where they came from. A source edited **without** a rebuild
produces rows measured on the OLD binary while `derived_from` records the NEW
source hash: **a green pin over a stale number, which is the exact defect the pin
exists to catch.**

Closed by **re-deriving, not by hashing** — `sweep_fit.py` now rebuilds the six
cells via `build.py::build_cell` before measuring, the way `asm.py::selftest`
re-derives the pilot's counts rather than trusting a recorded one. Measured:

```
rebuilt 6/6 cells at -O3 isolated: safe_naive safe_tuned unsafe verus c-gcc-h c-gcc
safe_tuned 0.3s   unsafe 0.3s   c-gcc 0.2s   verus 2.1s     (~3 s total)
REBUILD IS BIT-REPRODUCIBLE     (4 cells, sha256 unchanged across a rebuild)
```

`verus` is 2.1 s because `build_verus` **compiles**; it does not re-verify. The
binaries are deliberately **not** added to the digest: they are gitignored derived
artefacts, hashing them would downgrade a fresh clone to `MISSING-SOURCES`, and
once the rebuild guarantees provenance they add no detection power.

✅ **And the rebuild-then-measure run reproduced HEAD's rows and both fits exactly
— a clean negative: the binaries that were sitting in `.temp/build/p23/` WERE
current.**

   purpose, rule 3 says checks run locally, and 5.1 GB of mostly-rebuildable
