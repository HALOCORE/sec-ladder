## 1. `p25` — dynamic array with `realloc` growth. **ADMIT.**

**All four of the old kills are void or refuted, and two of them are refuted by
measurement rather than by the rule change.**

### 1.1 *"In `p25`'s shipped heap topology `realloc` NEVER moves"* — **FALSE as stated.**

`.temp/t143/p25/probe_when.c`, seed 4, doubling, 200 pushes, glibc 2.39:

```
topology ONE  (a single vector, nothing allocated behind it)
  4->8 in place   8->16 in place   16->32 MOVED   32->64 in place
  64->128 in place   128->256 in place                          1 of 6 MOVES

topology TWO  (a token vector and a string table grown in the same pass)
  4->8 in place   8->16 in place   16->32 MOVED   32->64 MOVED
  64->128 MOVED   128->256 MOVED                                4 of 6 MOVE
```

`probe_move.c`, 12 trials: ONE `11/48`, TWO `24/48`, identical across four draws.

⚠ **Even the single-vector topology moves.** `moved = 0/12` is not a property of
one vector; it is a property of a growth schedule that never crosses `16 -> 32`.
**And that is exactly the defect I hit myself**: my first adversarial input SAVEd
at `ntok = 4` and grew only `4 -> 8`, so R1 and R1h printed the same checksum and
the row looked dead. I found it with `probe_when.c`. I think this is the most
likely actual cause of `TASK_134`'s `0/12`, and it is recorded in
`.temp/t143/NOTES.md` as an instrument defect rather than quietly fixed.

A token vector plus a string table is what a parser does. It is not contrived.

`R1h` writes `if (curbase == toks)` and `R1` omits it. One conjunct, one load,
one compare, `+4 / −1` preprocessed lines. Re-deriving `toks[curi]` is a *second*
available hardened cell and is deliberately **not** the one shipped, precisely
because that one does change the addressing mode.

### 1.3 *"A nondeterministic R1 cannot be gated against `model.py` at all"* — **refuted by a BUILT ROW.**

block is"*, on benign inputs being stable everywhere, and on
`sanitizer_expect: fires` as the instrument for the UAF rows. `p25` is in exactly
that position. This kill was also ladder-side (`model.py` is the instrument).

## 2. `p28` — intrusive doubly linked list. **ADMIT.**

Old kill — *"safe Rust's answer is an arena that never frees, or `p27`'s
mechanism"* — is pure Rust-side. Void.

### 2.1 The C kernel

An LRU cache whose objects carry **two intrusive link sets**: a doubly linked LRU
list (`lp`/`ln`) and a singly linked hash chain (`hn`). The object is aliased by
two lists at once and **membership is not ownership**. `TRIM` reaches its victim
through the **LRU list**, so it holds no hash-chain cursor and must go and find
one. R1 does not.

**There is no table, no slot number, no `live[]` bit and nothing the input can
index.** The input names an object only by KEY and the program finds it by
walking. `p27`'s `h < ntab && live[h] == 1` has **no analogue, because there is
no `h`**.

### 2.2 The measurement

```

benign-trim       fix   5 builds      0   151520376         -           IDENTICAL
adv-uaf-read      bug   plain         0   151521027         -
```

ASan names the three lines: read at `body.inc:104`, freed at `:178`, allocated at
`:76`. `benign-trim` **exercises TRIM** and both rungs still agree — the benign
window is one where nothing walks the victim's bucket afterwards, which is
`p27`'s "benign windows never READ a closed handle" verbatim.

⚠⚠ **A property neither built temporal row has: `p28`'s R1 is REPRODUCIBLE on its
adversarial inputs (1 distinct value in 20 runs).** The links come first in the
struct — the Linux `list_head`-embedded-first layout — so glibc's tcache words at
user offsets 0 and 8 do not clobber `key`/`val`/`hn`. **So `p28` is gatable
against `model.py` on its adversarial inputs where `p27` and `p29` are not.**
Disclosed: with the payload first it would be ASLR-dependent, which is `p27`'s
situation.

### 2.3 The four questions

1. ✅ 2. ✅ 3. ✅ **The read path is CORRECT and the DESTROY path is INCOMPLETE
— the inversion of both built temporal rows**, whose free discipline is correct
and whose read is unguarded. The dangling pointer lives **inside another heap
object's link field**, not in a stack table (`p27`) and not in a stack local
(`p29`). 4. ✅

⚠ **The one honest weakness:** at 15 preprocessed lines this is the widest safety
line of the five. It shortens to 4 if the hash chain is doubly linked too
(`if (v->hp) v->hp->hn = v->hn; else bucket[vb] = v->hn; if (v->hn) v->hn->hp = v->hp;`),
which is also the *more* intrusive spelling. A build task should take that.

## 3. `p32` / `p33` — free-list allocator / object pool. **ADMIT, as ONE row with TWO arms.**

Old kill — *"safe slab == buggy C bit for bit"* + *"both storage choices already
ship as `p04` and `p27`"*. The first half is Rust-side **and is the result**; the
second half is a claim about the *Rust rungs'* storage, not about what the C code
does. Both void.

### 3.1 The C kernel

A pool of fixed-size blocks with a LIFO free list. A block is neither `malloc`'d
nor `free`d per use — it is POPPED and PUSHED, so the storage belongs to the
program from start to finish. A handle is a `(slot, generation)` byte. **Two bug
classes, one omitted conjunct, selected by the input** — `p29`'s shape:

- **FREE with a stale handle** → the block is pushed a second time,
  `nx[h] = freehead` with `freehead == h` makes the list **SELF-LOOP**, every
  later ALLOC returns the SAME slot, **two live handles ALIAS one block**, and the
  rest of the free list is lost.
- **READ with a stale handle** → the block has been recycled and the read returns
  the NEW occupant's payload.

### 3.2 The storage experiment — same source, one `#define`

`p32m/k.c` is two lines: `#define P32_MALLOC` then `#include "../p32/k.c"`. The
algorithm, the free list, the generations and the safety line are byte-identical.

```
input            C arena           C malloc                     safe Rust
                                                                #![forbid(unsafe_code)]
benign           37906190170       37906190170                  37906190170
                 silent            silent                                       IDENTICAL
adv-stale-read   31093             33573  ASan heap-use-after-  31093
                 ASan SILENT       free READ; plain 20/20                 arena == safe Rust
                                   DISTINCT
adv-recycle      962025            962025                       962025
                 ASan SILENT       ASan SILENT                        ALL THREE IDENTICAL
adv-doublefree   28444043583       rc=-6  glibc "free(): double 28444043583
                 ASan SILENT       free detected in tcache 2";            arena == safe Rust
                                   ASan attempting double-free
POSITIVE CONTROL fires in all four C builds (gcc/clang x plain/asan)
reproducibility  every arena row = 1 distinct value in 20 runs
```

⚠⚠⚠ **This is the sharpest thing in the task.** The exact sentence that killed
the row — *safe Rust reproduces the buggy C bit for bit* — is **confirmed
independently on a fresh kernel**, and it is now sharper than the version on
file: the *same C source* with `malloc` storage **aborts**, so the pair
(arena, malloc) is a controlled two-cell experiment on detector coverage with
everything else held byte-identical. `p29`'s headline is exactly this.

⚠ **And `adv-recycle` is identical in all three** — the use-after-recycle harm is
**storage-independent** and invisible to every allocation-shaped instrument. That
is `p29`'s recycle class, reproduced on unrelated code.

### 3.3 The four questions

1. ✅ 2. ✅ — with a detector, via the `malloc`-storage build of the same source;
the arena build's silence is the **finding**, and per the bar *"Miri/ASan does not
see it"* is a detector-coverage finding, never a kill. 3. ✅ **`p27` cannot
double-free** (it consults `live[]` on the free path), has no free list, no
recycling and no generation; and **the ALIASING harm — two live handles naming one
block, produced by a self-looping free list — has no analogue anywhere in the
built tree.** 4. ✅

**`p32` and `p33` are ONE row.** One C mechanism, two bug classes selected by the
input, one omitted conjunct — which is `p29`'s shipped shape. If only one arm can
be built, take **`p32`'s double-free/aliasing arm**: it is the more distant from
`p27`.

## 4. `p34` — reference counting. **ADMIT.**

Old kill — *"no inversion: C's own refcount leaks identically"* — is a claim about
the ladder's story, not about the C program. Void. It is also about a **different
omission**: the recorded `p34` work is a *leak*, and the class demonstrated here
is **premature free**, which this project has never measured on the C side.

### 4.1 The C kernel and why it is an inversion

Every object carries its own `rc`. `POP` decrements and frees at zero. `DUP`
publishes a SECOND reference and **R1 omits the matching `rc++`**.

```
p27   the free discipline is correct; the READ does not ask.        Fix the READ.
p29   the free discipline is correct; the READ does not revalidate. Fix the READ.
p34   THE READ IS CORRECT AND ASKS NOTHING WRONG.  A refcounted reference is
      valid by construction; it is the ACQUIRE that broke the invariant.
```

The free happens **early** rather than the read happening **late**. The safety
line is one statement, `+1 / −0` preprocessed lines — the tightest of the five,
`p27`'s tightness — and it sits at a site with **no bounded distance** to the
harm.

instrument-only row and a checksum row.
